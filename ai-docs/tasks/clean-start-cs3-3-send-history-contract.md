### Переходы и аварийные границы

1. **Send.** Проверить текст и отсутствие незавершённого intent. После генерации случайного ID выполнить read-only op 3 как проверку коллизии до публикации файла. Только строгое `Absent` допускает запись. При неожиданном положительном результате или отказе черновик остаётся несданным, op 2 не было. Затем опубликовать и перечитать `Prepared`, и только после этого вызвать op 2. В этой модели один владелец Setup, один UI writer и эксклюзивный runtime store. Read-only проверка не резервирует ID против стороннего IPC writer с доступом того же Windows пользователя.
2. **До op 2 или с неизвестным ответом.** Падение до публикации оставляет несданный черновик или staging остаток. Падение после публикации, timeout, отмена после постановки действия или потерянный ответ оставляют тот же `Prepared`. На явном Start/reopen и при «Уточнить» worker сначала вызывает op 3. Успешный `Absent` при `Prepared` включает кнопку «Повторить эту отправку». На нажатие снова op 3 и повтор той же операции с теми же байтами только при новом `Absent` и валидном допуске к локальной очереди. Поздний исход первого op 2 не создаёт дубликат благодаря тому же ID. Ошибка op 3 оставляет «Результат уточняется» и доступное уточнение. Повтор никогда не запускается автоматически.
3. **Runtime принял.** Валидный op 2 или op 3 с записью даёт `Accepted(queue_sequence)` в защищённом файле. Положительный op 3 не вызывает op 2. `0` показывает «В локальной очереди», файл остаётся. На `1` UI показывает «Сохранено в истории, доставка не подтверждена», на `2` — «Доставлено». Удалить pending только после проверенного op 3 с `event` и совпадающим `queue_sequence`, после перехода Accepted. Op 3 подтверждает запись в собственной проекции, поэтому загружать всю историю для удаления не нужно. Если соответствующая строка уже видна, сверить точный текст, роль и event до объединения. После commit до ответа, после ответа до записи Accepted или после Accepted до удаления, повторное чтение op 3 даёт тот же результат; файл, вернувшийся после незавершённой очистки, тоже только уточняется. Ошибка обновления/удаления оставляет запись и блокирует новый Send до успешной очистки.
4. **Конфликт.** `RequestIdConflict`, `Absent` после сохранённого Accepted, изменившийся `queue_sequence` или противоречащая история блокируют повтор. Пометить проверенный intent как `Conflict` атомарно с прежними bytes/ID, сохранить файл и показать «Отправка заблокирована. Сохранённая попытка требует проверки». При ошибке записи блокировка сохраняется в текущем worker. Op 3 не эхо текста, поэтому первичная проверка коллизии, single writer и защита файла существенны. Контракт не обещает восстановить запись о конфликте, если сторонний writer или rollback уже нарушили эти предпосылки и процесс погиб до записи Conflict.

## История, доступность и работа окна

Один проход истории в выбранном слоте начинается с пустого cursor, фиксирует snapshot frontiers `F` и следует причинному порядку из Runtime6. Порядок не пересчитывается по локальным часам, порядковому номеру другого автора или между слотами. Cursor — 275 opaque bytes из canonical base64url без padding (367 символов). Клиент проверяет длину, строгую каноническую форму и хранит cursor в RAM вместе с выбранным context, `view`, `F` и generation. Runtime аутентифицирует cursor и привязывает его к incarnation, context/dialog/epoch/session и view. На продолжении клиент требует прежние `view` и `F` до добавления строки. Дописывание новых событий не меняет зафиксированный snapshot. `finished=true` завершает проход, явное обновление начинает новый. InvalidCursor/SnapshotUnavailable требуют явного сброса страницы; неизвестная ошибка оставляет страницу с пометкой, что обновление не удалось. Новая selection, runtime instance или смена view сбрасывают локальный cursor и инвалидируют поздние результаты.
