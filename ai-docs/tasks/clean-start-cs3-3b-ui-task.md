## Product result

The fresh first-dialog desktop path supports composing and sending text to the established peer, seeing pending/delivery status and reading bounded pages of actual history. Keep explicit selection of the two immutable contexts for that same peer; do not silently remap contexts, create another account or pretend that these are arbitrary new contacts. Use the accepted typed Client2 and protected send lifecycle. Add a small typed worker-to-view projection for message identity/status/history rather than parsing progress strings. Keep draft text in RAM only. A click or successful UI-channel enqueue is not proof that the protected intent was saved: retain the draft until the worker confirms the corresponding submitted text is protected/accepted, and never clear a newer edit because an older completion arrives. Show the exact submitted pending text only in RAM backed by its protected intent, with separate unconfirmed, retry-available, queued, materialized and delivered states. Explicit retry uses the existing fresh-Absent/same-ID path; no automatic new-ID resend, cancellation of accepted messages or deletion/reset of an ambiguous attempt. A persisted pending record must become visible again after restart without requiring the user to remember the original text. State changes need exact Setup/context/request/role/event bindings. Merge the own pending/temporary result into its matching history row without hiding a peer row that happens to share a request ID.

## History and worker

- Use pages requesting up to 32 rows, the existing server byte budget and `finished`; a short page is not EOF. Keep at most 32 visible loaded rows for the selected context, one page per explicit action, and bounded RAM drafts/pending/temporary result as in the contract. Provide refresh and next-page controls. Starting at the beginning/manual refresh remains a stated pilot limitation; no unbounded drain or new latest-history protocol here.
- Preserve exact text and runtime causal order. Bind cursor/view/frontiers/context/runtime generation; invalidate on selection or runtime change. InvalidCursor/SnapshotUnavailable leads to an explicit refresh path. An error does not erase the last valid page or fabricate an empty successful history.
- Refresh delivery only for visible own messages with matching request/event; bound and coalesce work. Prioritize Stop/cancel and regular status over background refresh; retain one IPC in flight, fresh network badges and responsiveness. Delivered is the supported durable acknowledgement, never read. Disconnected state may retain a clearly historical confirmed delivery, not invent a new one.
- Keep file/DPAPI/IPC work off the render thread in the existing owned worker. Preserve Setup/Child ownership until observed exit, descriptor/PID/instance checks, late-result rejection and the existing startup/consent restrictions. Sending to the local runtime does not require a current peer lease; no local runtime means RAM drafting only.
- No plaintext message/history persistence in ordinary UI state, screenshots published to the repository, logs, Debug/error chains or generic diagnostics. Actual GUI evidence may show explicitly synthetic test text and must be described as such. No persistence of cursor/token/claim in a new UI database.
