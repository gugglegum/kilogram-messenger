# Sender runtime crash after durable materialization: контракт

2026-11-20. Baseline `b52bda60412610f86e77936ceb618d682d105b81`; graceful sender restart принят и опубликован. Сейчас только анализ исходников и этот контракт. Проверки доступности, тесты, fault/kill, deployment и изменение кода/Windows не выполнялись. Это **process crash после durable ack**, без заявления о power loss, прерванном commit или повреждении хранилища.

## Граница сохранности и последовательность

Runtime действительно владеет state: `runtime2/runtime.rs:1293` открывает `RuntimeRepository` под `StateDirectoryLock` и проверяет Device/context pins. Queue и Materialize — разные закрытые операции (`runtime2/data.rs:317,395`); Materialize сохраняет text/event/native transition и request projection через общий commit (`indexed_dialog/runtime2_ops.rs:851`). `IndexedDialogVault::commit_with_gate` использует redb `Durability::Immediate`, затем `tx.commit()` и только после успеха обновляет свой root/возвращает report (`indexed_dialog.rs:1176,1226,1245`). Backend sync вызывает `File::sync_all()` (`indexed_dialog/backend.rs:206`). Статус opcode3 читает repository request + delivery, где materialized означает существующий event/projection и durable Undelivered debt без receipt (`runtime2/runtime.rs:1654`, `runtime2_read.rs:122`). Защищённый frontend intent после materialized может уже быть удалён (`send_recovery.rs:469`): он не является предметом этой проверки.

Сценарий сохраняет принятый sender-restart порядок: свежие Setup/Auto/два контекста/пустые истории; штатно остановить B и доказать исчезновение runtime/socket; A materializes2, дважды сверить исходные request/context/event и полные локальные rows. После второго доказательства аварийно завершить **только runtime старого A**. Доказать его смерть и закрытие сокетов; штатно закрыть оставшийся frontend, сохраняя фактический аварийный результат. Обычным Connect запустить новый A на том же profile/state, с новым instance и advanced locator revisions. При Boff дважды проверить watching, исходные pending IDs, materialized/not-delivered и неизменные rows. Только затем Breturn, Auto, automatic queued2 без send/retry прежних requests, online replies2, exact4 events/final histories2/context/host. Уведомления ответов привязаны к новому A instance/epoch; accepted anchor rule и complete-set reconciliation всех old/new scopes сохраняются.

## Узкий fault mechanism: существующих primitives недостаточно

Иерархия: ordinary agent/session Job → attempt worker/Job → host owner/его Job → Chat → runtime. Host наблюдает runtime UDP из **своего** Job, сверяет image, сохраняет PID/creation time (`host.ps1:385–408`); observer дополнительно связывает runtime instance/token/status. Но существующие `CleanupChildren`, deadline cutoff и session guards завершают группы/служебные процессы и классифицируют ошибку; отдельной команды crash одного runtime нет. Использовать их как fault нельзя.

Минимальное предлагаемое дополнение harness: один opt-in, one-use runtime fault для A/первого Chat, привязанный к session/attempt/worker и owner generations/tag, исходному runtime PID/start/image+SHA, status instance и hash сохранённых pending proofs. Host owner удерживает handle проверенного runtime после socket/status binding; непосредственно перед fault снова проверяет живость, creation time/image и membership **своего** Job. Через этот же handle выполняет один `TerminateProcess(...,137)` и ограниченный wait≤5s/проверку exit137. 137 здесь фиксированный тестовый Windows exit code, отличный от watchdog124. Если процесс уже завершён, binding изменился или результат неизвестен — fault не доказан; не искать/убивать замену по PID или имени. Нельзя завершать Chat, host owner, attempt worker, agent или Job. Request/intent/result immutable, correlated и сохранены до разрешения следующей инкарнации. Реализация возможна небольшой функцией рядом с существующим handle/membership кодом `migration-s5-l1-deadline.ps1:79–113` и обработкой отдельного bound fault request внутри host loop; новая система fault gates не нужна.

Родительский `Session` удерживает собственный `Child`. После наблюдённого runtime exit `run_connected` прекращается; `Session::finish` при уже мёртвом child **не посылает shutdown**, reaps exit и drains (`connection.rs:1060,1573`). Поэтому поздний frontend Quit, посланный только после доказанной смерти runtime, не превращает опыт в graceful runtime shutdown.

## Ожидаемая авария и отдельное доказательство cleanup

Ниже — source-backed ожидаемый результат для одного old-A scope, который нужно подтвердить, а не предзаполнить в evidence:

| Scope | Требование |
| --- | --- |
| Old A runtime | Handle-bound injected exit137, process/signaled и socket gone; отсутствуют runtime_stopping/runtime_network_stopped/runtime_final. Их присутствие требует разбора, а не автоматического PASS. |
| Old A connection/worker | Оба parent final records обязательны: exit137, reaped/EOF/drains complete, forced=false; connection was_running=false, ack_attempted/ack=false, exit_success=false; worker saved_ok=true, stop_graceful=false. |
| Old A Chat/host | Ожидаются фактические Chat exit3 + Quit `cleanup_unconfirmed`, mailbox_quit=false, но чистый EOF/streams; host exit1 и исходный failed receipt. Job membership, before/after empty, forced=false, work_expired=false обязательны. |
| Остальные scopes | Прежние exit0/ack/EOF/все5 mandatory typed finals/descriptor cleanup/нефорсированные пустые Jobs обязательны. |

Причина Chat exit3: `Chat::disconnect_until` требует graceful runtime exit0 и исчезнувший descriptor (`chat.rs:348`); coordinator отвечает `cleanup_unconfirmed` и выбирает code3 (`terminal_chat/coordinator.rs:549,727`), mailbox признаёт Quit только при ok=true (`mailbox.cs:208`). Host сохраняет этот факт и выходит1, а не выдаёт искусственный успешный receipt.

Сейчас `Lab-OwnerClean` отвергает такой owner; worker прекращает attempt с `LAB_OWNER_FAILED`, а следующий owner требует всех предыдущих state=clean (`lab-agent.ps1:32,155–160,375–377`). **Нужна узкая expected-runtime-crash ветка**, отдельная от неизменного normal predicate: разрешить продолжение только при matching one-use intent + доказанном injected exit + перечисленных parent/host/empty-Job доказательствах. Хранить state вроде expected_crash_reconciled, не переименовывать в graceful clean. A должен отчитаться2normal clean owners +1expected crash, B —3normal clean; global/native cleanup остаётся closed/empty/nonforced/noerror. Любая другая ошибка/неполный cleanup блокирует restart. Общий unknown/forced/timeout/error catch не является допустимой классификацией аварии.

## Same-profile recovery и stale descriptor

OS locks удерживаются handles, а не существованием lock-файла (`kilogram-state/src/lib.rs:385`); normal acquire вызывает recovery. Старый frontend должен полностью выйти и освободить свой Setup lock. Никаких ручных удалений lock/descriptor/history, сброса профиля или новой учётной записи.

При abrupt death IPC server Drop/shutdown не исполняется, поэтому старый descriptor может остаться. Production start проверяет его account/device, создаёт **свой** child, ожидает отличный подписанный descriptor и связывает Status с новым child/instance (`connection.rs:835,868,898,955`); publish использует sync + temporary.persist (`runtime-ipc/src/lib.rs:2284`). Existing profile bytes/digest проверяются (`connection.rs:259`), failed-stop сам по себе не блокирует новый процесс. Это обоснование ожидаемого normal recovery, ещё не фактический результат.

Есть дополнительный harness prerequisite: `Normal.start:120–132` и `observe.ps1:180–200` сейчас отвергают **любой** preconnect descriptor. Для одного доказанного crash-restart нужна отдельная проверка: disconnected Chat без runtime/socket, только неизменный exact stale descriptor hash того самого умершего runtime; после обычного Connect — новый descriptor/instance с прежними account/device/context/profile pins. Не удалять файл ради старого predicate и не разрешать произвольный чужой descriptor. Нормальный preconnect остаётся строгим. Если production recovery не срабатывает, сохранить FAIL и вернуть причину, не чинить профиль для PASS.

## Diagnostics, ресурсы и review

Host reader уже допускает один exact previous PID/instance scope без требования полного набора finals (`host.ps1:160–210`). `shutdown_records` декодирует/проверяет все bytes/nonce/PIDs, но его completeness требует5kinds, а OfflineRecipient collector превращает неполноту в capture error. Переиспользовать decoder, сохранить raw complete=false/missing и классифицировать **только три отсутствующих runtime finals old A** отдельным crash verdict. Parent finals и established startup records обязательны, rejected/malformed/partial/unknown файлы — FAIL. Replacement/все B scopes проверяются обычным oracle. Нельзя глобально отключать capture errors.

Ожидаемые record counts: old A startup9+parent finals2=11, new A13 →24+marker=25; B14+13+marker=28. Это оценка, не новое измерение. Writer32records+marker/reader≤16 current,≤32 при explicit previous, distinct retained PIDs и immutable files сохраняются; unknown/PID collision не перезаписывать. Mailbox192commands/512frames, no retry, sends2/0/0/2. Fault control — отдельная bounded команда, не пользовательский IPC Send.

Сохраняем native1000/1015, reserve60, controller1800/1860, BelowNormal/max2, Connect85/local watching30/proofs35/gates90/probe60/mincall2. Graceful baseline application522.266s/controller640.391s; один fault wait≤5s и bounded parent close помещаются в предполагаемый запас, но remaining budget проверяется до fault/restart, а лимиты ради PASS не повышаются. Reuse прежних product EXE; продуктовых изменений пока не выявлено. После review нужны focused real-sequence/negative-binding/expected-fault classification checks, затем отдельная concrete activation.

Изменение agent owner policy меняет installed payload. Текущий bin update заменяет только6 inputs, а уже работающий agent держит прежние функции. Следовательно, подготовка должна отдельно предъявить безопасное versioned payload refresh/idle stop/restart A и fresh identity/pins (существующий TaskSpec/path/LeastPrivilege без task/firewall/UAC изменений), с сохранением/восстановлением прежнего payload. Source установки предоставляет обычному SID Modify на agent directory (`lab-install.ps1:813–815`), TaskSpec использует прежний фиксированный script/config path; это позволяет предложить ordinary refresh, не новую установку. Фактические права/доступность сейчас не проверены. Это prerequisite для activation, сейчас такой refresh не выполняется и не считается разрешённым этим контрактом. Новых source/build/run/installation механизмов сверх узкого изменения не предлагать. Полные пути/hash/blob проверенных исходников: `.tmp/terminal-t1-3e/sender-crash-contract-01/source-facts.json`.
