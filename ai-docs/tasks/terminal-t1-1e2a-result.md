# T1.1e2a. Исполнитель, writer и подтверждение истории

База `4ba72879ac82c522c49c984c81c9f8dbd4bfb88d`. [Контракт E2](terminal-t1-1e-contract.md)

Терминал использует прежние worker, writer и управляющую очередь. Фоновая работа учитывается до фактического возврата по её тегу. Запрос отмены сразу доступен через координатор. Новый job с общим `Chat` ждёт возврата предыдущего. Если фоновая работа не освобождает worker в срок, закрытие идёт через существующий `SessionStop` и общий бюджет T1.1c.

Кадр привязан к epoch, пачке и своему индексу. Writer проверяет tag и приоритет под коротким mutex, затем освобождает его до write и flush. Устаревший кадр пропускается. Кадр, уступивший команде, возвращает те же байты владельцу. Оба исхода обходят путь подтверждения и ошибки потока. Пока запись физически не завершилась, её кредит остаётся учтённым. В E2a кадры и фон подаются через тестовые hooks. Производственного polling, вывода входящих событий и resync ещё нет.

При занятом уведомлением writer допускаются только `status`, статус запроса и `history`. Send/retry, локаторы и другие команды используют прежний барьер. Тег поколения команды освобождает correlation ID перед первым байтом результата. Поздний ACK другого поколения не завершает новую команду. TTY request ID ожидается отменяемо и разрешает send только после записи и flush в действующем поколении. Отмена до допуска writer убирает объявление. Если кадр уже начал записываться, его поздний результат не допускает send.

Внутренний proof страницы содержит context, исходный курсор, view, frontiers, возвращённый курсор и поколения команды и подключения. У последней страницы закрытый курсор сохраняется во внутреннем proof. Публичная форма истории остаётся прежней. Продвижение разрешено после write и flush в срок. Прерванное чтение, слишком большой результат, несовпавший, неуспешный или просроченный ACK не дают proof.

## Проверки

- `build04` успешно собрал CLI с `--locked --offline`, Cargo Idle и одним заданием. SHA-256 постоянного `target/terminal-t1-checks/kilogram-cli.exe` — `792f56899179d383d4e202d304f9df047672d867c2d1209c9406e8cf74dc0be0`.
- `cli04` выполнил 18 проверок терминала через стабильный harness. Детерминированные барьеры покрыли чтение и cancel при занятом уведомлении, прежний допуск send/retry/locator, предотвращение запоздалого TTY notice, запрет перекрытия worker, сохранение кредита при write timeout, возврат отложенного кадра, устаревшее поколение и исчерпание счётчика. Отдельная проверка различила завершённую в срок запись с поздним наблюдением и запись после дедлайна. Прежние повторы correlation ID, ограничения вывода и продолжение истории прошли в том же запуске.
- `console02` прошёл Ctrl+C на активной команде и в простое через приватную Windows ConPTY. После отмены активной команды stdin принимал следующий status. Перед проверкой выхода драйвер получил `target_not_active` через `/cancel`. Ранний `console01` отправлял Ctrl+C сразу после наблюдения ответа status и не дождался выхода в срок. Повтор использовал те же EXE, добавив подтверждение простоя.
- `fixture03` подготовил свежие Setup и проверил два реальных пути отмены отправки, после чтения защищённого намерения и после приёма runtime. Для сетевого прогона использованы эти Setup.
- `smoke02` прошёл реальный Windows loopback в обоих контекстах. В терминалах owner и observer подтверждены отправка, restart, повтор correlation ID при позднем возврате worker, TTY request ID до отправки, запрет записи у observer и штатная очистка при EOF, заблокированном и закрытом stdout. Дополнительное чтение из реального observer через IPC подтвердило proof первой и последней страниц после ACK. Закрытый курсор принят существующим E1 follow.

У пяти зачётных запусков дочерний процесс и обёртка вернули 0. Получен EOF обоих потоков, Job пуст, принудительной остановки не было. Для первого варианта сохранены EXE, `cli02` и `smoke01`. После него добавлено время фактического write/flush в ACK и проверка, что timeout фоновой задачи не меняет уже начатое штатное закрытие. Ранние обёртки сборки и CLI harness с отдельным процессом `vctip` сохранили свои логи. Окончательные проверки использовали закреплённые стабильные пути и свежие Setup.

Сборка тестовых harness обновила промежуточный `verification/kilogram-cli.exe`. Продуктовые проверки запускали копию из `build04` по стабильному `target/terminal-t1-checks/kilogram-cli.exe`. Её хеш совпал в сборке, ConPTY и сквозном прогоне. Манифест фиксирует этот образ и фактически запущенные harness.
