## Decisions to settle from actual source

1. Map the existing Runtime2 IPC operations and Runtime6 durable state to typed client methods and UI behavior. Inspect send (op 2), request status (op 3), history (op 4), request/delivery lookup and queue semantics. State actual version/opcode/shape validation, identity binding, message limits, outer/inner limits, history cursor rules and bounded memory use. The current client owns a verified descriptor; preserve that same-descriptor identity/token/address boundary and worker generation/cancellation rules.
2. Persist a stable random 16-byte request ID before IPC submission, bound to the exact local account/device/claim/context/slot and exact submitted text. After timeout or lost reply, query the original ID before a retry; never create a new ID automatically for an ambiguous send. Specify absent/queued/materialized/delivered results and conflicting request reuse. Preserve original bytes rather than silently trimming or normalizing on retry.
3. Choose the smallest adequate protected local pending-intent design. Inspect existing storage and Windows protection APIs; `key_provider.rs` currently protects vault master keys and is not automatically an arbitrary-blob public API. Compare reuse of an existing seam versus a small focused protection wrapper. Do not invent cryptography or add a broad state/CLI/Iroh dependency merely to share DTOs. A bare message hash is dictionary-testable and is not confidentiality. Ordinary UI files/logs must not contain plaintext messages, pending text or history. Clearly state the local protection threat model, tamper/substitution behavior and limits against rollback; do not promise rollback resistance from encryption alone.
4. Define atomic persistence, bounds, cleanup and recovery for crashes before IPC, after runtime commit but before response, and after response but before local acknowledgement/cleanup. Distinguish unsent drafts from submitted pending intents. Decide explicitly whether drafts survive restart; avoid promising persistence that is not implemented. Specify what happens if the protected record is unreadable, corrupt, belongs to another profile or cannot be durably written. The UI must not offer an apparently safe automatic new-ID resend after ambiguity.
5. History currently excludes unmaterialized queued items. Define a minimal consistent pending/history presentation, stable identity and deduplication, delivery-status refresh and cursor invalidation handling. Delivered means the supported durable acknowledgement, never read. Bound page sizes against worst-case UTF-8 and JSON escaping: do not assume a page of 16 maximum-sized messages fits. Prefer a conservative verified cap before adding adaptive machinery.
6. Preserve CS3.2b ownership and lifecycle guarantees: one connection worker, no blocking render thread, no stale response changing a new selection, Child and Setup held until observed child exit, and no false active/delivered label after expired status or failed admission. State the behavior when disconnected or offline, and whether sending requires a local runtime.
