# CS3: fresh Windows onboarding и первый диалог — контракт для review

2026-11-10. Baseline `f7fd176d33c93eebe79d4d6fa0df385eca111290`. Только source/design review: реализации, сборок, тестов и commit нет. CS1/CS2 приняты; legacy `create` с раскрытым `vault-meta-v1` failure не является prerequisite. Ниже предлагаются изменения, а не уже существующие возможности UI.

## Решение и честный результат

Рекомендую **CS3.1: «Создать приглашение / Присоединиться», recoverable bootstrap и сохранение публичного ответа**. Пользователь действительно создаёт защищённый аккаунт, сохраняет фразу и получает файл для следующего шага; экран заканчивается состоянием «Ожидаем ответ / Подтверждение собеседника». Он не запускает legacy reader и не сообщает, что чат уже готов.

Это явно обозначенный пилот первого диалога: один аккаунт, первое устройство, одна пара собеседников, две заранее закреплённые context slots. Создание аккаунта без привязки к первой паре context IDs и произвольное добавление контактов требуют отдельного изменения текущего runtime. Не создавать новый аккаунт на каждый контакт, не предлагать «добавить ещё контакт» этим же способом, не пересоздавать аккаунт при несовпадении contexts. Slot0 показывать как первый диалог; slot1 закреплён за той же парой и не является свободным местом для другого контакта.

Полный результат CS3 после трёх slices: два пользователя создают fresh stores, сверяют публичные идентификаторы, подписывают существующий CS1 consent каждый своим Root, запускают Runtime6 и обмениваются сообщениями через UI. На одном ПК это loopback acceptance. Два компьютера требуют отдельно проверенного relay-маршрута; готовность удалённой связи не следует из локального smoke.

## Create/invite/join: contexts прежде обоих bootstrap

1. **Alice: «Создать приглашение».** UI генерирует два различных CSPRNG 32-byte context IDs; не просит вводить hex. Вызывает CS2 `create-ordered2 --workspace-dir NEW --context C0 C1`. До bootstrap Bob/device/peer неизвестен: нет placeholder credential или authenticated contact. После успешного one-shot результата Alice сохраняет фразу и явно подтверждает это. Затем экспортируется публичное приглашение с её настоящими credentials/floor и точным ordered `[C0,C1]`. Состояние: «Передайте файл будущему собеседнику».
2. **Bob: «Присоединиться по приглашению».** До создания своего аккаунта bounded parser проверяет вид файла, contexts, credential Root signatures/account/device binding, authority floor. Показывает Alice Account ID/device и предупреждение о недоверенном источнике. Bob сверяет их с Alice по независимому известному каналу и подтверждает именно эту пару. Только затем CS2 создаёт Bob с **тем же ordered `[C0,C1]`**, Bob сохраняет фразу и экспортирует публичный ответ. Если у Bob уже есть несовместимый fresh store — отказ с объяснением ограничения пилота, без смены слотов/нового аккаунта в фоне.
3. **Alice импортирует ответ.** Он обязан ссылаться на её invitation ID, contexts и account/device, не на произвольный другой workspace. Alice независимо сверяет Bob Account ID/device, подтверждает привязку первой пары; сохраняется неизменяемый peer selection. После первой подписи нельзя принять другой reply/peer вместо выбранного. До этого предложение остаётся ожидающим, не «аутентифицированным чатом».
4. **Роли вычисляются после появления обоих настоящих device IDs:** canonical role0 — меньшие 32 bytes device ID, не inviter и не имя пользователя. Для обоих contexts выполняются отдельные неизменённые CS1 propose/cosign/import.

| Роли | Обмен после invite |
|---|---|
| Alice=role0 | Bob возвращает credentials/floor → Alice после проверки Bob выполняет `context2-propose` дважды → Bob проверяет и `context2-cosign` дважды, импортирует final → передаёт final Alice → Alice импортирует |
| Bob=role0 | Bob после своей проверки Alice/ack phrase может включить два proposals в reply → Alice сначала проверяет Bob, затем `context2-cosign` дважды и импортирует → возвращает final Bob → Bob импортирует |

CS3.1 экспортирует reply только с public identity; добавление proposals в CS3.2 допустимо, но не меняет порядок подтверждений. Каждый вызов получает **только свой** `--account-dir`, собственные expected account/device, peer expected account/device, конкретный context, оба public credentials и отдельно удерживаемые floors. У proposer фиксируются not-before/TTL (не более текущих 30 суток) для byte-identical retries. [CS1 verifier](E:/AI-Projects/kilogram-p2p-messenger/apps/kilogram-cli/src/ordered_dialog/runtime2/fresh_consent.rs:24) сохраняет canonical roles, Fresh body/domain/suite/origin, membership, current local Root, floor/rollback/conflict и expiry checks. Не использовать старый `context2-create` с двумя Root paths.

В UI явные этапы «Ожидаем данные», «Сверьте собеседника», «Ожидаем подпись», «Оба согласия установлены», «Подключаемся». Proposals не импортируются как final. Offline `context2-import --state-dir … --expect-account LOCAL --expect-claim LOCAL --invitation-file FINAL` выполняется при остановленном runtime для обоих слотов. Частичный успех одного slot сохраняется; повтор проверяет тот же final, не удаляет store. До обоих imports Profile2/start недоступны. Runtime admission повторно проверяет действительность, поэтому истёкший/отозванный consent не становится пригодным из-за старого UI-флага.

### Публичный файл, а не новый security protocol

Один bounded JSON envelope `version=1`, `kind=invite|reply|proposal|final|locators`, random invitation ID, mode `ordered-dialog-v2`, ordered contexts, sender account/device, optional exact intended recipient pins, и только разрешённые для kind artifacts. Credentials/authority/proposals/finals/locators — исходные bytes в canonical lowercase hex; чужие filenames, пути, команды, IPC descriptors/tokens, local claim и private keys не принимаются/не экспортируются. Не разбирать archive и не выполнять ссылки из файла. Локальные пути назначает приложение, outputs no-clobber.

Предлагаемые caps: envelope ≤512KiB, deny unknown/duplicate fields; credential/floor по16KiB decoded; proposal/final по96KiB, ровно два в ordered slots; Locator2 по8KiB. Перед allocation проверять encoded length и общий budget. Для каждого kind — точный набор/количество полей, distinct contexts, строгие IDs и matching credential pins. Экспорт только после локальной валидации. Не доверять утверждению envelope о роли, имени, подписи, expiry или адресате; криптографическую проверку выполняют существующие parsers/verifiers.

Invitation не является согласием и не доказывает, что отправитель — знакомый человек. Первые public identity/floor bytes становятся локальными pins **после** внешнего сравнения; позднее нельзя понижать удерживаемый floor. Snapshot не доказывает «самую последнюю в мире» authority revision. Показывать полные сравнимые account/device fingerprints без ручного hex-ввода; проверять также неизменность пары contexts/ID приглашения. Не вводить новый SAS/подпись envelope. Пока собеседник не проверен и оба final не установлены, send выключен.

## Recovery phrase, helpers и продолжение после остановки

Новый consumer вызывает fixed trusted bootstrap executable напрямую argv, без shell; sibling executable default [уже существует](E:/AI-Projects/kilogram-p2p-messenger/apps/kilogram-windows/src/lib.rs:214), test fixture задаёт fixed verified paths явно. Проверить выходной mode/version, workspace и contexts через CS2 codec. Предел secret stdout64KiB действует **во время чтения**, stderr отдельно bounded и не цитируется в ошибках; concurrent readers не блокируют pipes. Предлагаемый helper watchdog60s с завершением/wait только собственного child при timeout/cancel/закрытии. Это необходимая новая малая process adapter работа, не уже доказанная возможность старого wrapper. Не использовать generic wizard error formatter для phrase-bearing output.

Output/phrase живут в `Zeroizing`; view не Clone/Serialize/обычный Debug, не попадает в saved egui state, журнал, crash diagnostics или clipboard. Показывать только на специальном recovery экране; нет copy по умолчанию. Явное «Я сохранил слова отдельно» открывает «Скрыть и продолжить», после чего phrase удаляется из state; drop/close/ошибочный или поздний worker result также очищают буферы. Не обещать очистку всех внутренних renderer/OS copies или защиту от screenshot. Сохранённый локально public onboarding record содержит только пути/IDs/stage/artifact pins и факт acknowledgement, не phrase.

До acknowledgement нельзя экспортировать invite/reply или начинать signing. Если helper/GUI завершился после ready commit и фраза не получена/не подтверждена, аккаунт на диске может быть завершён, но recovery не подтверждено. На reopen показать этот факт, не «фраза сохранена», не получать её повторно и не повторять bootstrap в том же destination. Продолжить можно только если пользователь подтверждает, что действительно сохранил фразу до остановки; иначе дальнейшая ceremony заблокирована. Если пользователь решит отказаться от этого пробного аккаунта, это отдельное явное действие и новый путь, без автоматического удаления/пересоздания. Existing incomplete/unknown stores всегда сохраняются и отвергаются для create. Public onboarding manifest — UI progress, не замена Runtime6 enrollment/ready verification; при конфликте не запускать runtime.

Copy: «Эти слова восстанавливают ключ и идентификатор аккаунта. Для актуальных полномочий нужен отдельный пакет и последняя контрольная запись; переписка сохраняется отдельно». Existing `account-recovery-export`/inspect и [worker adapter](E:/AI-Projects/kilogram-p2p-messenger/apps/kilogram-windows/src/lib.rs:2195) совместимы с account-root; package/witness сохраняются отдельно от phrase, witness — независимо. После ceremony/root mutations предложить свежий export; не называть export резервной копией сообщений.

Все unresolved intents ограничены (например64), при записи/разборе ошибки отправка блокируется. В runtime DB/wire ничего добавлять не надо; это не обещание сохранения несданного draft. После Delivered metadata можно явно завершить. Приёмка этого узкого локального metadata решения нужна вместе с контрактом CS3.3; чисто RAM retry не удовлетворит reopening requirement.

## Маршруты, история и volunteer storage

[RouteConfig2::effective](E:/AI-Projects/kilogram-p2p-messenger/crates/kilogram-transport-iroh/src/ordered2.rs:20) требует loopback bind для DirectOnly/Auto; Auto без relay становится DirectOnly. LAN/public bind сейчас отвергается. RelayOnly требует explicit canonical relay URL и **отсутствия bind**; у peer Locator2 должен быть тот же разрешённый relay. Ни default discovery, ни произвольный relay из приглашения не включать: endpoint builder очищает адресные/relay transports и добавляет только конфигурацию. На двух компьютерах наиболее узкий существующий кандидат — согласованный RelayOnly с реально доступным Iroh relay; это transport relay, не центральное хранение сообщений. До отдельной two-device проверки UI помечает режим пилотным, direct режим — «два окна на этом компьютере».

Двухустройственная приёмка позже: два independent fresh stores/Roots, конкретный разрешённый relay и реальные подписанные Locator2; authenticated Active2 у обоих, сообщения/Delivered/history в обе стороны, graceful reopen и обновлённые locators. Не расширять bind policy или добавлять новый transport ради UI smoke. Наличие URL/успешная локальная relay регистрация не доказательство этой проверки.

История принадлежит пользователю и остаётся в его защищённом Runtime6 device store; UI не создаёт общий сервер истории. Требование default-on bounded volunteer storage сохраняется ([RFC0083](E:/AI-Projects/kilogram-p2p-messenger/docs/RFC-0083-default-volunteer-blind-storage-role.md)); старый [UI default](E:/AI-Projects/kilogram-p2p-messenger/apps/kilogram-windows/src/lib.rs:741) true. **Fresh Profile2/IPC сейчас не содержит volunteer role/settings**, ordinary provider/mailbox operations там отвергаются. Нельзя переносить checkbox true как будто feature работает или молча менять продуктовый default на false. В пилоте явно «Хранение для других участников ещё не подключено в этом режиме»; подключение требует отдельного контракта и не делает миграцию prerequisite. Этот gap и one-peer limitation исключают заявление о полном MVP.
