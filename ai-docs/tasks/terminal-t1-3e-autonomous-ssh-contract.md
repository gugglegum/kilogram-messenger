**Разовая подготовка.** После инженерной приёмки конкретного установщика выполняется один provisioning на A и B; выбранный пользователем срок жизни правил уже разрешён и повторного запроса разрешения не требует. Если Windows запрашивает UAC для этого установочного шага, пользователь подтверждает его один раз на каждом хосте. Установщик сохраняет исходные профили и правила, добавляет только два собственных scoped allow-правила на каждом узле и включает нужный Private-профиль. Сейчас Private выключен, добавление разрешений само его не включает. Точная привязка, эффективный профиль, сохранение SSH и отсутствие изменений Public/VPN входят в проверку provisioning. Включение Private действует на профиль целиком: до изменения проверяются все использующие его интерфейсы и применимость существующих правил. Если это затронет VPN или SSH, установщик останавливается до изменения. Новый канонический baseline с Private On и этими правилами формируется и проверяется явно.

Имена предлагаются отдельные, `Kilogram-Lab-AllowDiscovery-A/B` и `Kilogram-Lab-AllowIroh-A/B`, с owner-тегом кампании. Фиксированный диапазон соответствует текущей проверенной конфигурации динамических UDP-портов и допускает restart с новым портом. Перед provisioning диапазон и адреса проверяются. Обновление EXE идёт под тем же путём с новым проверенным хэшем. Обычный cleanup не удаляет эти правила и не переключает профиль. Короткого срока жизни у allow-правил нет.

**Обычный запуск.** Рекомендуется по одному заданию Task Scheduler на хост, которое запускает постоянный обычный агент под точным тестовым SID с `InteractiveToken`, `LeastPrivilege`, фиксированными action/path и без сохраняемого пароля. Задание создаётся однократно вместе со стендом, получает logon trigger и запуск по требованию через обычный SSH. Идентификатор попытки и команды поступают агенту через существующий файловый mailbox, а не через свободные аргументы задания. Агент переиспользует Run-Ordinary, проверки token/session/DPAPI-контекста и существующие Jobs. Для исполнения нужен вошедший в Windows тестовый пользователь. Документация разрешает регистрацию задания для собственного пользователя с интерактивным типом без пароля, а исполнение ограничивается существующим интерактивным сеансом. [Microsoft о security context](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks), [типы logon](https://learn.microsoft.com/en-us/windows/win32/api/taskschd/ne-taskschd-task_logon_type).

На A и B выполнена только синтаксическая проверка явного XML через `TASK_VALIDATE_ONLY=1`. Она прошла под текущими обычными токенами, задания до и после отсутствовали. Регистрация, исполнение задания и DPAPI из этого задания ещё не проверены. Первый COM-builder XML дал ошибку 0xC00CEE2B, его наблюдения сохранены. У явного XML итоговый результат успешный. Синтаксическая проверка не регистрирует задание по контракту API. [Microsoft о validate-only](https://learn.microsoft.com/en-us/windows/win32/api/taskschd/nf-taskschd-itaskfolder-registertaskdefinition).

После review пилот проверяет запуск именно из задания, SID, nonadmin, PID/start/image, session/logon, загруженный профиль и synthetic DPAPI roundtrip, затем реальный Setup create/status/quit и runtime IPC. В наблюдавшихся ранее условиях SSH Protect дал Win32 5, а обычный интерактивный B прошёл roundtrip. Это конкретная разница контекстов на этом стенде. Утверждение, что DPAPI принципиально недоступен по SSH, из неё не следует. Продуктовое защищённое хранилище остаётся штатным.

**Ручные действия после подготовки.** Обычные попытки запускаются целиком через SSH. После logout/reboot пользователь выполняет обычный вход тестовой учётной записью в Windows, агент стартует по logon trigger. Существующее задание можно повторно вызвать по SSH после завершённого сбоя агента, без нового UAC. При отсутствии нужного интерактивного сеанса контроллер сообщает session unavailable и ждёт входа. Альтернатива без задания — один обычный запуск долгоживущего агента на сеанс Windows, но после его аварийного выхода снова нужен ручной старт. Основной выбранный вариант — задание с обычным агентом.

Одна автоматическая попытка состоит из следующих шагов.

1. Контроллер проверяет агента, SID/session, boot/session nonce, отсутствие активной предыдущей попытки и relevant свойства постоянных правил через доступное обычному пользователю чтение. Полный последний административный Audit сохраняется с временем и хэшем. При недоступности нужных свойств, смене сети, диапазона, профиля или правил попытка останавливается с диагностикой. Новый baseline молча не принимается.
2. В свежем `runs/<attempt>` создаются одноразовые тестовые данные. Manifest задаёт хэши CLI/bootstrap/helpers. При необходимости EXE заменяется по обычному SSH только после пустых Jobs и освобождения файлов. Агент держит file locks на время попытки, затем освобождает их. Установщик задания и allow-правила от хэша очередного EXE не зависят.
3. Агент принимает только фиксированные операции begin/status/setup/chat/cancel/end и stop-agent в собственном test root. Один attempt на хост, generation/nonce/PID/start связывают ответы и запрещают replay и двойной owner. B сам назначает локальные monotonic/UTC пределы попытки. Прежний источник deadline из административного gate S для обычного suite заменяется этим ответом агента.
4. Функциональный suite проверяет свежий Auto LAN setup, текущие четыре lease, runtime/token/socket proof, watching до отправок, сообщения в двух контекстах, restart B и обоих узлов, offline pending при остановленном peer, retry с теми же request/event ID, историю и отсутствие повторов. Восстановление незавершённой попытки начинается с reconciliation её сохранённых receipts. Новая попытка использует свежие данные. Для функционального admission измеряется собственный срок подключения, а измерение от Release остаётся в fault-suite.
5. Каждая попытка завершает владельцев через quit, получает exit/EOF/empty Job/нет IPC, закрывает recovery/Setup-фильтры и сохраняет итог. При потере контроллера локальный watchdog ограничивает попытку и выполняет owned cleanup. Ошибки оставляют первичную причину и отдельный результат очистки. Агент остаётся готовым к следующей попытке только после подтверждения отсутствия предыдущих owners. Правила и Private сохраняются между попытками.

**Отдельные сетевые сбои.** Остановка peer проверяет application offline и последующую доставку. Реальная потеря UDP, expiry lease, удержание/Release и административный rollback остаются отдельным fault-suite при изменениях transport/discovery/firewall или перед соответствующей приёмкой. Он использует отдельные временные block-правила с независимым локальным watchdog и прежними bounded hold/rollback. Постоянные allow-правила в его cleanup сохраняются. Старый firewall script требует Private Off и при cleanup удаляет собственные allows, поэтому повторно использовать его без адаптации к Private On и раздельному владению нельзя. Полный Audit и ограниченный административный запуск нужны только этому редкому suite.

**Окончание кампании.** Отдельный явный teardown останавливает агент после пустых Jobs, удаляет только совпадающие по имени/owner/фильтрам правила кампании и её ordinary task. Затем сверяет результат и восстанавливает исходное состояние Private из provisioning-описи, если профиль с тех пор не был изменён пользователем или политикой. Несовпадение сохраняется для разбора, чужое состояние не перезаписывается. Подготовка и teardown требуют административных прав, обычные повторы их не требуют.

Минимальное изменение исходников затрагивает пять участков. В `interactive-field.ps1` внешний цикл агента обслуживает несколько attempts, сохраняя нынешние per-attempt Jobs и защищённый Setup bridge. В `interactive-field.py` меняются адресация agent/attempt и источник deadlines. В `driver.py` добавляется отдельный обычный suite, использующий нынешние send/retry/history/identity проверки. В `observe.ps1` добавляется read-only проверка постоянного lab baseline. Один фиксированный provisioning/teardown script устанавливает ordinary task и два allow-правила. Изменения fault-script ограничиваются отделением временных blocks и восстановлением baseline Private On. Искусственные ответы gate в обычном suite не используются.

Следующая реализация сначала проходит review и локальные lifecycle проверки, затем одноразовый provisioning и пилот двух последовательных SSH-попыток без ручных запусков между ними. Цикл test → fix → retest после этого выполняется автономно в рамках принятого scope. Новый установщик, задания, правила и поле на этом этапе не запускались.
