# T1.1c. Отмена команд и завершение терминальной сессии

Предложение для архитектурной проверки. База `a68e544236a793dc769426286cde70eacf055469`. Границы проводного формата, владения Setup и защищённого намерения заданы в [контракте T1](terminal-t1-contract.md) и [отчёте T1.1b](terminal-t1-1b-result.md).

## Состояние на базе

- `read_commands` блокируется на `SyncSender::send` после заполнения очереди. Главный цикл синхронно ждёт `Frontend::execute`, а затем до 3 с ждёт запись и flush. Поэтому даже распознанные EOF или следующая управляющая строка могут ждать за обычной командой. R1 освобождает correlation ID непосредственно перед первой записью результата. Только подтверждённый flush успешной истории продвигает курсор. [Чтение и запись](https://github.com/gugglegum/kilogram-messenger/blob/a68e544236a793dc769426286cde70eacf055469/apps/kilogram-cli/src/terminal_chat.rs#L627) · [Главный цикл](https://github.com/gugglegum/kilogram-messenger/blob/a68e544236a793dc769426286cde70eacf055469/apps/kilogram-cli/src/terminal_chat.rs#L701)
- `Chat::request` ждёт готовую область до 6 с и ответ worker ещё до 30 с. Observer синхронно ждёт IPC через свой Tokio runtime. `Work::cancel` выставляет флаг завершения всей принадлежащей сессии и пробует положить `Stop` в обычную очередь. `cancellable` опрашивает флаг через интервалы 20 мс. Он прерывает ожидание IPC, а вызовы Store остаются синхронными. [Chat](https://github.com/gugglegum/kilogram-messenger/blob/a68e544236a793dc769426286cde70eacf055469/crates/kilogram-first-dialog/src/chat.rs#L113) · [Флаг Work](https://github.com/gugglegum/kilogram-messenger/blob/a68e544236a793dc769426286cde70eacf055469/crates/kilogram-first-dialog/src/connection.rs#L1300) · [Ожидание IPC](https://github.com/gugglegum/kilogram-messenger/blob/a68e544236a793dc769426286cde70eacf055469/crates/kilogram-first-dialog/src/connection.rs#L478)
- `Store::prepare` возвращается после записи, синхронизации, публикации и чтения DPAPI intent. Публикация может произойти раньше ошибки чтения. Для `retry` Recovery сначала ищет прежний ID через runtime, а при допустимом повторе берёт исходный текст из Store. После отправки текущее чтение ответа повторно проверяет состояние сессии. При внедрении отмены подтверждённый receipt должен пережить опоздавшую отмену, сохраняя независимую проверку descriptor, slot и instance. - В `Session::finish` есть 5 с на IPC shutdown, до 10 с ожидания выхода, ещё 5 с после kill принадлежащего дочернего процесса и до 5 с на EOF его потоков. При отсутствии наблюдаемого выхода `Cleanup::observe_exit` продолжает ждать. На верхнем уровне `Chat::disconnect` уже имеет предел 30 с и блокирует новый owner при неподтверждённом завершении. Поэтому предел CLI и подтверждение reaping должны остаться разными условиями. ## Команды и состояния

JSONL принимает `{"v":1,"id":"cancel-1","op":"cancel","args":{"target_id":"work-1"}}`. Требования к обоим ID те же, что для correlation ID версии 1. При исправном stdout исходная операция и принятая команда cancel получают ровно по одному `result`. Результат cancel коррелируется с `cancel-1` и возвращает `target_id`. Результат исходной операции коррелируется с `work-1`. У send/retry он также сохраняет `context` и `request_id`.

| Состояние цели при распознавании cancel | Результат cancel | Судьба исходной операции |
| --- | --- | --- |
| Активная | `ok: true`, `value.state: requested` | Устанавливается флаг её экземпляра. Операция получает один собственный итог по таблице ниже. |
| Активная, запрос отмены уже установлен | `ok: true`, `value.state: already_requested` | Ранее выбранный путь отмены продолжается. |
| Принята в очередь, выполнение ещё не началось | `ok: false`, `code: target_queued` | Остаётся в очереди. Cancel действует на активную команду. |
| Итог уже зафиксирован, ID ещё удерживается до первой записи | `ok: false`, `code: target_completed` | Зафиксированный итог сохраняется, включая результат успешного send. |
| Нет такой цели или итог уже начал публиковаться и ID освобождён | `ok: false`, `code: target_not_active` | История завершённых correlation ID не хранится. |
| ID самой cancel-команды совпал с занятым ID | Отдельный `frame_error: duplicate_id` | Существующий запрос и его резервирование сохраняются. Самоссылка со свободным ID даёт `invalid_args`. |

У операции есть внутреннее поколение. Допуск очередной команды и выбор цели cancel читают одну коротко блокируемую таблицу, а переходы `running → cancel_requested` и `running → completed` упорядочены относительно друг друга. Запрос отмены привязывается к поколению при распознавании строки и не переносится на позднее переиспользование ID. По проводу `target_id` обозначает текущую активную операцию. Клиент, переиспользующий ID после ответа, прекращает отправлять отмены для его предыдущего использования. Writer освобождает ID и занятый слот cancel или диагностического ответа перед первым байтом, пока единственный предыдущий ответ принадлежит потоку записи. Flush не очищает следующее резервирование. Новая мутация всё равно ждёт ACK. Поздний результат проверяет поколение и не публикуется второй раз. Cancel может получить результат раньше исходной команды.

TTY `/cancel` запрашивает отмену текущей активной команды, в простое сообщает об отсутствии цели. Первый Ctrl+C во время активной команды делает тот же запрос. Повторный Ctrl+C до её итога не завершает сессию. Пока готовый результат ожидает записи, завершение команды уже выиграло гонку. В простое, когда нет ни выполняемой команды, ни её результата в записи, Ctrl+C начинает штатный выход CLI. Символ ETX во входном pipe не считается консольным событием.

## Итог исходной операции

| Граница, которую подтвердил исполнитель | Итог после запроса отмены |
| --- | --- |
| Успешный или определённый ошибочный итог уже получен, включая проверенный receipt | Обычный итог. `queued`, `materialized` и `delivered` берутся из имеющегося подтверждения. Полученный receipt проходит проверки привязок независимо от флага отмены. |
| Чтение или attach остановлены до подтверждённого итога | `ok: false`, `code: cancelled`. Частичная страница не публикуется, курсор не меняется. Отменённый attach освобождает свой клиент, а отменённый start закрывает только создаваемого им владельца. |
| Новый send, отмена выиграла перед входом в публикацию intent | `ok: false`, `code: cancelled_not_submitted`, с ID и контекстом. Эта попытка не публиковала intent и не начинала send IPC. Ранее известный запрос под тем же ID по-прежнему проверяется через status. |
| Выполнение вошло в публикацию, readback не подтверждён | При отсутствии определённого результата `ok: true`, `state: unconfirmed`, `protected: null`. Синхронный вызов Store может закончить публикацию. |
| DPAPI readback подтверждён, подтверждённого receipt нет | `ok: true`, `state: unconfirmed`, `protected: true`, с исходными ID и контекстом. Сохранённый intent остаётся доступен для status/retry. После отметки отмены новый IPC send не начинается. |
| IPC мог уйти, ответ не получен или не прошёл проверку привязок | `state: unconfirmed` и последнее доказуемое значение `protected`. Возобновление начинается с `request_status` того же ID. При подтверждённом отсутствии запроса и доступном сохранённом intent `retry` использует его точные ID и текст. |

Флаг и вход в `Store::prepare` имеют общую точку принятия решения непосредственно перед вызовом. Если публикация уже началась, даётся завершиться штатной записи и проверке. Следующая точка решения находится перед первым polling send IPC. Выигравшая отмена закрывает допуск. Если допуск уже выиграл, IPC мог уйти и применяется строка с неопределённым результатом. Пропажа ожидания не отзывает принятое сообщение. Уже имеющийся durable intent у `retry` исключает ответ `cancelled_not_submitted`. Сверка и штатные переходы существующего intent допустимы после проверенного receipt. Пропажа ранее подтверждённого локального файла сохраняет блокировку Recovery. Формат DPAPI, хранилища и IPC остаются прежними.

## Управление и сроки

Оставить один последовательный исполнитель обычных команд, один поток блокирующего stdin и один поток записи stdout. Короткий координатор обрабатывает изменение состояния, сигналы, completion и таймеры отдельно от `Frontend::execute`. Reader передаёт управление без блокировки. `cancel`, `quit`, `disconnect`, EOF и ошибка чтения адресуются через тот же короткий управляющий путь, независимо от обычной очереди и выходного ACK. EOF не требует места в выходных слотах. Writer по-прежнему один и пишет без mutex состояния.

- Допустить одну выполняемую и одну ожидающую обычную команду, с зарезервированным ответом у каждой. Выделить ещё три малых слота: один для результата cancel, второй для результата quit/disconnect и третий для `busy` или ошибки framing. Reader продолжает принимать управление при занятой обычной очереди. При переполнении слота отказа или cancel прекратить допуск и начать закрытие с кодом 2. Для уже допущенных команд зарезервирован собственный итог даже в этом случае. Сериализовать по одному результату до 256 КиБ и не накапливать страницы истории. Бюджет подтверждения записи каждого результата 3 с. Новый send/retry начинается после подтверждения предыдущего итога и, для TTY, объявления нового ID. Если stdout закрыт в простое, отказ обнаруживается при следующей попытке записи. Фоновая проверка pipe не входит в этот срез.
- Передавать per-command флаг и абсолютный deadline в слой `Chat`, в рабочие операции History/Request и в ожидания IPC observer. Использовать общий `cancellable` с проверкой флага сессии и флага операции, включая проверку до первого polling IPC. GUI может продолжать передавать только прежний флаг сессии. Для send/retry флаг и последний подтверждённый этап публикуются исполнителем отдельно от итогового ответа, чтобы координатор мог составить консервативный итог по дедлайну. Ожидание Windows DPAPI или файлового вызова остаётся синхронным внутри исполнителя.
- Начальный бюджет команды после допуска к исполнению 10 с для чтения и status, 45 с для start, 30 с для send/retry. Вложенные ожидания ограничены остатком общего бюджета, без последовательного сложения прежних таймаутов. Управляющий запрос регистрируется независимо от IPC. При читаемом stdout целевой предел ответа на cancel 1 с при свободном writer, либо остаток текущего 3-секундного окна записи и его собственное окно. После запроса отмены дать исполнителю до 2 с на подтверждённый итог, затем использовать таблицу выше. Если рабочая операция ещё не ответила, сохранять её внутренний слот за тем же поколением до фактического ответа. Новая мутация не пересекается с предыдущей; закрытие и наблюдение за выходом остаются доступны.
- При EOF, `quit` или ошибке потока сразу запретить новый допуск, снять ожидающую команду с `session_closing` и отменить активную по таблице. Явный `disconnect` проводит те же действия для текущего подключения и после подтверждения возвращает в состояние без сессии. При EOF уже допущенная, но ещё не начатая строка может завершиться с `session_closing`, включая последнюю строку без LF. Пакетный клиент держит stdin открытым до получения нужных результатов. При отказе stdout запускать закрытие сразу после ошибки записи либо по её 3-секундному дедлайну. Ни читатель stdin, ни застрявший writer не входят в обязательное ожидание при выходе процесса.
- Для закрытия owner передать независимый `stop_owned_session` с начала запуска `Work`, чтобы координатор сигнализировал stop даже до первого статуса и при занятой очереди. Публикация stop handle предшествует запуску работы. Отдельная короткая проверка перед spawn разрешает его или подтверждает, что ребёнок не стартовал. При уже выданном допуске к spawn закрытие ждёт результат запуска и завершает только созданный Work runtime. Запущенное подключение остаётся предварительным до фиксации итога `connect`. При проигрыше отмене предварительный owner закрывается, а предварительный observer освобождает клиент. `cancel` другой команды сохраняет уже подключённую сессию. У observer закрытие снимает ожидание IPC и клиент, без `shutdown` владельца.
- Абсолютный предел закрытия CLI 30 с от первого триггера. Пока вывод исправен, оставить последние 3 с для итогового ответа `quit` или `disconnect`. К 27-й секунде результат owner подтверждён только при собственном shutdown, наблюдаемом выходе и reaping, EOF дочерних потоков и снятии собственного descriptor. При нехватке подтверждений выдать `cleanup_unconfirmed`, код процесса 3 при выходе и защёлку против нового owner до конца текущего CLI. Принудительное завершение собственного child остаётся fallback существующего Work, с отдельным наблюдением выхода. Неподтверждённый reaping, принудительный stop и ошибка привязки не засчитываются как штатный cleanup. Успешное закрытие через EOF, idle Ctrl+C или `quit` даёт 0, неисправный ввод или вывод при подтверждённом cleanup даёт 2. При одновременных ошибках неподтверждённый cleanup имеет приоритет.

## Windows и предпосылки проверки

Workspace уже включает Tokio `signal`. Lockfile закрепляет Tokio 1.53.3. В локальном исходнике этой версии `tokio::signal::windows::ctrl_c()` регистрирует подписку через `SetConsoleCtrlHandler` и возвращает `io::Result` при создании. Для локального TTY с консольным stdin подписать CLI до `ready` и передавать событие в короткий управляющий путь. Ошибка регистрации в этом режиме даёт код 2 до запуска владельца. Для ввода по pipe опираться на команды и EOF. Владелец уже запускает runtime с `CREATE_NO_WINDOW`. GUI и SSH-noPTY сохраняют собственные пути управления. [Workspace](../../Cargo.toml#L68) · [Lockfile](../../Cargo.lock#L6420) · [Флаги дочернего процесса](../../crates/kilogram-first-dialog/src/connection.rs#L512) · [Windows Console signals](https://learn.microsoft.com/en-us/windows/console/ctrl-c-and-ctrl-break-signals)

Тест клавиши использует приватную ConPTY с принадлежащим тесту процессом CLI и отдельным Job Object. Драйвер посылает Ctrl+C только через её вход после сигнала готовности. Предварительно подтвердить, что изолированный дочерний процесс действительно получил Ctrl+C при включённом processed input. `GenerateConsoleCtrlEvent(CTRL_C_EVENT, nonzero_group)` не доставляет Ctrl+C целевой группе, а нулевая группа охватывает процессы общей консоли. `CTRL_BREAK_EVENT` может адресоваться группе, но является другим событием. При недоступной ConPTY отметка о тесте клавиши остаётся открытой до изолированной локальной проверки. В SSH-noPTY отдельно проверить протокольный cancel и реакцию на EOF с закреплённым хостом. [GenerateConsoleCtrlEvent](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent) · [Process creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) · [CreatePseudoConsole](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole)

С отдельным барьером после проверенного receipt подтвердить победу `queued` или более сильного статуса над запоздалой отменой. |

Позднее старое поколение не отменяет новое и не освобождает его ID. |
| EOF, quit и отказ вывода во время работы | Заблокировать обычную операцию барьером, заполнить обычную очередь, отдельно прекратить чтение stdout либо закрыть его. Подтвердить, что stop достигает Work независимо от очереди и writer, ожидающий send не начинает IPC и процесс выходит в пределах бюджета. Для исправного stdout проверить итог каждой допущенной команды, включая отдельный ответ quit. Для задержанного reaping проверить 3 и запрет нового owner после неподтверждённого disconnect. |
| Observer и Ctrl+C | Отменить запрос observer на управляемом барьере IPC, затем завершить observer и проверить доступ к прежнему owner и его историю. В собственной ConPTY проверить активный и idle Ctrl+C, повтор во время активной отмены и выход при блокирующем stdin. |
| Регрессии | Повторить R1 framing, корреляцию и курсор, T1.1b настоящий DPAPI и retry на свежей паре. Использовать test-only барьеры и подтверждения стадии, без случайных sleep. Сетевые harnesses запускать через стабильный Windows runner с Cargo Idle и одним заданием. |

## Решения архитектурной проверки

- Итог фиксируется один раз атомарно со снимком поколения, стадии и подтверждённого receipt. Receipt, учтённый до фиксации, имеет приоритет над консервативным итогом. Более поздний receipt обновляет обычный Recovery и доступен через status. Внутренний слот остаётся занят до фактического завершения, даже когда cancel уже получает `target_completed` или результат опубликован и correlation ID свободен. Такое состояние исключено из определения idle Ctrl+C.
- Код 3 означает отсутствие подтверждения. Защёлка действует до выхода текущего CLI. При новом процессе существующие Setup и runtime state locks защищают единственность живого владельца. Lock и descriptor не очищаются вручную для обхода этой проверки. Отдельный supervisor и сохраняемый маркер не требуются. [Setup lock](../../crates/kilogram-first-dialog/src/model.rs#L77) · [Runtime state lock](../../apps/kilogram-cli/src/ordered_dialog/runtime2/runtime.rs#L993)

На этапе предложения выполнена проверка исходников и Windows API. Запуск реального Ctrl+C, реализация, входящие уведомления, locator UX, onboarding и полевой LAN остаются за пределами этого контракта.
