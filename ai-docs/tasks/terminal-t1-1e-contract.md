# T1.1e2. Входящие уведомления терминала

Контракт для архитектурной проверки на базе `4ba72879ac82c522c49c984c81c9f8dbd4bfb88d`. Наблюдение за двумя контекстами готового Setup использует [опубликованный E1](terminal-t1-1e1-contract.md) и действующие `Chat`, coordinator и writer. Явная история, сетевой протокол, IPC и хранилище сохраняются. [Общий контракт](terminal-t1-contract.md) · [Отмена и завершение T1.1c](terminal-t1-1c-contract.md)

## Подключение и расписание

- Открыть новое поколение наблюдения `epoch` после успешного результата connect, его write/flush ACK и фактического завершения connect job. Закрепить проверенные `runtime_instance`, два ID контекстов и `ChatStatus::own_roles` для обоих слотов. Владелец получает роли из `DialogScope`, наблюдатель из сверенного `Status2`. Закрытие или подтверждённая смена привязки сразу делает epoch недействительным. Peer offline/restart при действующем локальном instance сохраняет позиции. [Источник ролей и scope](../../crates/kilogram-first-dialog/src/chat.rs#L156)
- По каждому контексту начать с `anchoring`. Первый успешный anchor фиксирует watermark и переводит в `watching`. События до серверного среза anchor остаются в явной истории. События после него доступны через follow, включая append до получения ответа anchor. Если история ещё не создана, показать `waiting_history` и повторять anchor раз в 2 с. `connect` и `live_admitted` имеют собственную семантику готовности. Наблюдение обоих контекстов действует независимо от `/use`.
- Допускать максимум одну фоновую задачу на существующем worker, с интервалом между стартами не меньше 250 мс и дедлайном 5 с на задачу. Каждая вызывает один метод E1/Chat для anchor, follow или страницы. Неизменившийся контекст проверять через follow не чаще раза в 1 с. После открытия диапазона читать его следующую страницу при первой подходящей очереди и свободном бюджете. Выбирать готовые контексты round-robin после каждого допуска. Занятый контекст уступает другому. Таймеры встроены в цикл координатора, отдельного polling loop нет.
- Для `Unavailable` повторить ту же операцию и входной курсор через 1, 2 и 4 с после фактического завершения задачи. Четвёртый подряд отказ переводит контекст в `resync_required(runtime_unavailable)`. Успех сбрасывает счётчик. `HistoryCursorInvalid`, неожиданный view/scope, неправильная форма ответа или исчезновение ранее доступной истории сразу означают resync. E1 может вернуть `Unavailable` при замене descriptor. Тогда действует тот же ограниченный повтор, автоматического attach к новому instance нет. `HistoryPositionUnsupported` переводит оба контекста текущего runtime в `unsupported` с причиной `history_follow_unsupported`. Явное чтение остаётся доступным.
- Обычный `status` добавляет локальный `monitor` с epoch и состоянием каждого известного контекста. Возможные состояния `anchoring`, `waiting_history`, `watching`, `retrying`, `resync_required`, `unsupported`. Для `retrying` показывать номер повтора, для разрыва и недоступности код причины. В JSONL это необязательное верхнеуровневое поле результата status, доступное и при ошибке status IPC. В TTY состояния выводятся вместе с результатом или ошибкой. При disconnect epoch пуст, а накопленный resync остаётся виден. Без известной области список пуст. `status(request_id)` сохраняет старую форму.

## Чтение, резерв и ACK страницы

Координатор владеет watermark завершённого среза, подтверждённым курсором внутри открытого диапазона и всеми кредитами вывода. Worker владеет `Chat` и непереданным результатом. Writer получает буфер кадра без копирования. Теги разделяют epoch подключения, поколение задачи и поколение пачки, а для ACK кадра ещё и индекс внутри пачки. Командные correlation ID остаются у существующего `Active`.

| Переход | Условие и эффект |
| --- | --- |
| Допуск задачи | Сохранить ревизию ожидаемой позиции и входной курсор. Для страницы зарезервировать байты и записи до запуска. Во время ожидания результата общий `Chat` занят. |
| Завершение или вытеснение | Foreground запрашивает отмену фонового `OperationControl` и ждёт `retired` после фактического возврата метода Chat, включая завершение ожидания действия Work. При вытеснении сохраняется входной курсор и не расходуется попытка retry. По дедлайну результат отменён, после retirement действует обычный backoff. Если retirement отсутствует через ещё 2 с после отмены, перейти в штатный close с причиной `worker_unretired`. Общий сервис повторно используется только после retirement. Поздний или отменённый результат освобождает свой резерв после retirement. Он не меняет позицию и не создаёт пачку. |
| Допуск пачки | Принять только результат текущего epoch и задачи с ожидаемой входной позицией. Проверить context/view и закреплённые frontiers, непрерывность ordinal обеих ролей и совпадение `finished` с достижением обеих границ. Отобрать строки peer по проверенной роли и дедуплицировать по `(context,event_id)` внутри пачки. Передать всю страницу атомарно и вернуть неиспользованную часть резерва. В пределах контекста одновременно существует максимум одна готовая или записываемая пачка. |
| Подтверждение страницы | Каждый успешный write+flush освобождает принадлежащий кадру кредит. Только ACK последнего кадра действующей пачки фиксирует её результирующий курсор. Последняя страница диапазона дополнительно меняет watermark завершённого среза. Страница без peer-событий подтверждается сразу после проверок. Новый follow не начинается, пока текущий диапазон не дочитан и его последняя пачка не подтверждена. |
| Разрыв или поздний ACK | Отбросить кадры, запись которых не началась. Уже начатый кадр может выйти с прежним epoch. Устаревший ACK освобождает лишь свой кредит, если запись действительно закончилась. При неоднозначном префиксе страницы сохранить предыдущий полностью подтверждённый курсор и выставить resync. Повторное чтение не печатает потенциально записанный префикс автоматически. |

Память для уведомлений ограничена **64 событиями и 256 КиБ кодированных данных** вместе с резервами, готовыми кадрами и записью в полёте. Из них два места по 512 байт зарезервированы для сигналов resync, независимо от очереди данных. При отсутствии резерва чтение страницы откладывается. Из оставшегося бюджета брать `limit = min(8, свободные записи, floor(свободные байты / 25 КиБ))`. За одну страницу резервируется до 200 КиБ. Смена epoch и отмена сразу освобождают только буферы, которыми ещё владеет координатор. Переданные worker/writer буферы остаются учтены до возврата.

4096 байт UTF-8 в худшем случае расширяются до 24 576 байт при экранировании. У компактного JSONL-кадра ниже оболочка с LF занимает максимум 322 байта, в том числе три 64-символьных ID и 20 цифр epoch. Максимум кадра 24 898 байт. У TTY максимум 24 596 байт с оболочкой и LF. Легальный текст помещается в резерв 25 КиБ. Сериализовать непосредственно в ограниченный буфер кадра. Промежуточная IPC-страница ограничена E1, память не растёт с длиной диапазона. Если валидный по форме результат нельзя закодировать в зарезервированном размере, отклонить всю пачку и выставить `resync_required(output_bound)`. [Лимит текста](../../crates/kilogram-protocol/src/ordered_dialog_v2.rs#L28)

## Writer и явное восстановление

- Оставить один writer. Управляющие и командные результаты и объявление TTY request ID имеют приоритет. Уведомление стартует только при отсутствии выполняемой или ожидающей foreground-команды и готового управляющего/командного кадра. При равной готовности пачки чередуются между контекстами. Writer проверяет epoch и приоритет перед допуском к первому байту, затем пишет без mutex. Устаревший кадр возвращает `skipped`. При появлении команды до допуска текущий кадр переносится обратно в пачку с тем же резервом. Ни один из этих исходов не считается ошибкой stdout или ACK.
- Уже начатый кадр не прерывается ради следующего. Во время него разрешить выполнение foreground-чтения (`status`, request status, `history`) на свободном worker с существующим резервом ответа. ACK прежнего командного результата по-прежнему нужен для освобождения его `Active`. Send/retry остаются за прежним барьером запуска. Новый TTY send получает подтверждённое объявление request ID до допуска к записи намерения. Ожидание объявления должно реагировать на cancel/close даже до передачи notice в writer. Использовать ограниченное ожидание с проверкой `OperationControl`, привязать объявление к поколению команды и снимать ожидающее объявление при отмене. [Путь объявления](../../apps/kilogram-cli/src/terminal_chat/coordinator.rs#L532) · [Dispatch и writer](../../apps/kilogram-cli/src/terminal_chat/coordinator.rs#L741)
- `cancel` адресуется пользовательской команде. Ctrl+C без активной команды, EOF и quit идут по прежнему пути закрытия. Disconnect, EOF и отказ stdout сразу отменяют фон и сигнализируют `SessionStop`, даже если writer занят или worker ещё возвращается. Нельзя прочитать ACK раньше завершения write/flush. Через 3 с без ACK срабатывает ошибка stdout, общий бюджет cleanup 30 с. Результат очистки и код выхода сохраняют семантику T1.1c. [Отмена и закрытие](../../apps/kilogram-cli/src/terminal_chat/coordinator.rs#L270) · [ACK и дедлайн](../../apps/kilogram-cli/src/terminal_chat/coordinator.rs#L666)
- Resync липкий, хранится отдельно от очереди по контексту и поколению разрыва. Он переживает disconnect/reconnect в том же терминале. Неявный anchor после такого разрыва не заменяет его. Сигнал выдаётся отдельным кадром один раз на разрыв в действующем epoch при доступном writer. Новый процесс начинает с anchor. Пропуски между запусками проверяются явной историей.
- Снять resync можно после явной `history` с первой страницы, допущенной в действующем epoch после начала этого разрыва. Новая цепочка фиксирует `epoch, context, gap, view, frontiers` и ожидаемый следующий курсор. Каждая страница продолжает ровно предыдущую подтверждённую страницу и засчитывается через write/flush ACK. Новая первая страница заменяет прежнюю цепочку после ACK. Только подтверждённый `finished` этой цепочки передаёт закрытый E1 cursor в watermark. Курсор, открытый до разрыва, случайный `finished`, неправильное поколение или смена snapshot не снимают флаг. `response_too_large`, отмена, выигравшая до фиксации результата по T1.1c, и отсутствующий либо поздний ACK сохраняют последнюю подтверждённую страницу и watermark. Повтор допустим с того же токена и меньшим limit. В исправном режиме явная история не двигает наблюдение. [Подготовка вывода истории](../../apps/kilogram-cli/src/terminal_chat.rs#L638)

TTY печатает одну строку `Incoming [chat 2]: <text>` или `Chat 2: resync_required (<code>). Use /history.`. JSONL печатает один компактный объект на LF. Для входящего это поля `v:1`, `type:"event"`, `event:"incoming"`, `epoch` как `u64`, `runtime_instance`, `context`, `event_id`, `text`. У сигнала `event:"resync_required"` вместо ID события и текста есть `code`. Correlation ID у событий отсутствует. Экранировать C0/C1, переносы строк и bidi-управление, включая `U+061C`, `U+200E/U+200F`, `U+2028–U+202E` и `U+2066–U+2069`. JSON decode восстанавливает исходный текст. Дедупликация относится к непрерывной сессии с подтверждаемым выводом. ACK подтверждает запись в поток. Явная история остаётся источником сверки. Stderr не получает сообщения. [Текущий TTY экранировщик](../../apps/kilogram-cli/src/terminal_chat.rs#L506)

## Проверки и порядок реализации

Сейчас coordinator держит диспетчеризацию команды до свободного writer, а объявление TTY request ID ждёт ACK в worker. В `HistoryAdvance` есть следующий токен, но завершённая позиция исчезает. Предлагаю два небольших diff в рамках E2. Сначала добавить к текущим worker/Flight теги, retirement и ACK, приоритет writer и внутренний proof последней страницы с регрессиями coordinator. Затем подключить наблюдение, новый вывод и полную цепочку восстановления. Отдельная очередь команд, второй worker, второй writer и новый IPC не нужны.

| Проверка | Наблюдение |
| --- | --- |
| Anchor и длинный delta | На готовых тестовых Setup накопить историю. До anchor строки остаются в обычной истории, append после anchor появляется один раз. Хвост длиннее 128 строк принимается страницами. Проверить оба контекста, свои и peer роли, смену `/use`, TTY/JSONL и 4096 байт текста с максимальным экранированием. Проверить round-robin и отсутствие проб до due. |
| Peer restart и смена epoch | Peer offline/restart доставляет queued event одному живому локальному terminal по одному разу. Отдельно заменить локальный instance и подать задержанный результат и ACK со старым тегом. Ни позиция, ни новая пачка не меняются. Проверить отсутствие нового допуска до реального retirement и ограниченные повторы `Unavailable`. |
| Soft и blocked stdout | При временно занятом уведомлении чтение выполняется, cancel принимается, очереди остаются в бюджете. Send соблюдает барьеры предыдущего результата и TTY request ID. При полностью остановленном stdout проверить EOF/quit, 3 с write deadline и штатный cleanup. |
| Явный resync | При invalid cursor/view или частичной записи сохранить флаг и позицию. Ещё открытая старая цепочка, потерянный ACK, отмена и слишком большая страница флаг не снимают. Начать новый snapshot после разрыва, дочитать до подтверждённого конца и получить следующее событие. Проверить `unsupported` и изоляцию второго контекста. |

Проверки Windows используют свежие тестовые копии и стабильный `scripts/run-cargo-tests-stable.ps1`. Физический LAN и onboarding относятся к следующим этапам. Реализация ждёт приёмки этого контракта.
