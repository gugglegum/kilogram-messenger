# T1.1e. Входящие уведомления терминала

Проект для архитектурной проверки. [T1.1e1](terminal-t1-1e1-contract.md) добавляет read-only anchor/follow к общему сервису. T1.1e2 добавляет наблюдение обоих контекстов готового Setup поверх принятого e1. Стороны проверяются локально. Onboarding и физический LAN остаются отдельными этапами. [Общий контракт терминала](terminal-t1-contract.md) · [Отмена и завершение](terminal-t1-1c-contract.md)

## T1.1e2. Прогресс уведомлений

- После подтверждённого `connect(start|attach)` взять anchor для каждого контекста. Он устанавливает исходный watermark без вывода старой истории. При ещё не созданной истории показывать `waiting_history`. Точка отсечения — первый успешный anchor. Уже сохранённые к этой точке строки доступны через `history`. Оба контекста наблюдаются независимо от `/use`, сетевой offline peer сохраняет действующую локальную позицию.
- Периодический follow при неизменном watermark читает только метаданные. При росте он возвращает start cursor фиксированного диапазона. Единственная фоновая задача делает один короткий вызов за раз, чередует контексты, ждёт обычного темпа polling и уступает командам. Для каждой страницы проверить scope/view/frontiers и непрерывность ordinal от ожидаемой позиции по обеим ролям. Уведомлять только о записях peer. Дедупликация использует `(context,event_id)` в текущей пачке, подтверждённый курсор и неизменяемые позиции между страницами. Повтор результата задачи с тем же входным курсором не создаёт новую пачку.
- Использовать подтверждаемые **страницы** вместо накопления всего диапазона. Аутентифицированный start cursor уже закрепляет его границы, а строки проверяются до выдачи каждой страницы. Весь набор событий одной страницы допускается в очередь атомарно. После write и flush последнего кадра этой страницы зафиксировать её непрозрачный курсор как позицию возобновления. `watermark` завершённого среза меняется только после подтверждённой последней страницы. Страница без подходящих строк обрабатывается как подтверждённая пустая пачка. Пока предыдущая страница ожидает ACK, для контекста не читать следующую и не вызывать follow, иначе можно потерять границу незавершённого диапазона. Такой порядок позволяет прочитать хвост длиннее 128 сообщений без роста памяти с длиной хвоста.
- Общий лимит подготовки, очереди и записи в полёте — 64 события и 256 КиБ закодированных данных. Чтение берёт небольшую страницу, например до восьми строк, при наличии резерва под её худший размер. При занятом резерве отложить чтение, сохранив входной курсор. За пределами очереди существует только одна ограниченная IPC-страница и один буфер кодирования кадра. Переполнение после применения допустимого размера, постоянный отказ чтения, нарушение среза или разрыв привязки выставляют `resync_required`. Ошибка вывода после части страницы оставляет позицию на предыдущей полностью подтверждённой странице. Повтор чтения не должен автоматически перепечатывать потенциально записанную часть. Нужна сверка явной историей по ID. Гарантия дедупликации относится к непрерывной исправной сессии, ACK stdout подтверждает write и flush.

## Поколение, resync и управление

- Status показывает отдельно по контекстам `waiting_history`, `watching` или `resync_required` с кодом причины, даже если вызов status IPC завершился ошибкой. Флаг resync хранится в памяти процесса вне очереди и переживает disconnect/attach в том же терминале. При смене подключения или instance закрыть поколение наблюдения и отбросить его поздние ответы, очередь и ACK. Уже начатый кадр может дойти со старым поколением. Разрыв сохраняет последнюю подтверждённую позицию до resync. Новый процесс начинает с anchor. История остаётся доступной для пропусков между запусками.
- Восстановление начинается после вывода сигнала resync или получения этого состояния в status. Открыть явную историю затронутого контекста и дойти до подтверждённой последней страницы одного snapshot в текущем поколении. Её завершённый cursor заменяет watermark только этого контекста. Прерванное чтение, просроченный или чужой cursor и ошибка вывода сохраняют resync. Флаг выдаётся отдельно, когда writer способен принять управляющий кадр. Явное чтение в исправном состоянии не перескакивает позицию уведомлений.
- Команды и управляющие ответы имеют приоритет над уведомлениями с отдельными зарезервированными слотами. Фоновое чтение уступает исполнителю через `OperationControl`. Поздний ответ от отброшенной задачи не применяет прогресс. Обычная отмена относится к пользовательской команде. EOF, close и ошибка stdout сразу вызывают `SessionStop` независимо от заполнения очереди или writer. Уже начатая запись имеет прежний дедлайн 3 с, cleanup — общий бюджет 30 с. При занятом stdout обработка управления продолжается, сохраняются существующие барьеры ACK для send/retry и объявления TTY request ID. Эти ожидания прерываются cancel/close. [Путь writer](../../apps/kilogram-cli/src/terminal_chat/coordinator.rs#L666)

TTY выводит одну строку `Incoming [chat 2]: <text>` или `Chat 2: resync_required (<code>). Use /history.`. JSONL выводит один объект на LF без correlation ID. Событие содержит `v:1`, `type:"event"`, `event:"incoming"`, `epoch` (поколение наблюдения), `runtime_instance`, `context`, `event_id`, `text`. У `event:"resync_required"` вместо ID и текста есть `code`. TTY экранирует управляющие символы, переводы строк и bidi-управление. JSONL экранирует те же символы с сохранением исходного текста после decode. Stderr не получает содержимое сообщений. [Текущий экранировщик](../../apps/kilogram-cli/src/terminal_chat.rs#L506)

Приёмка e2 на свежих тестовых копиях проверяет baseline на накопленной истории, delta длиннее 128 строк и уведомления обоих контекстов при любом `/use`. Проверить offline и restart peer, повторы доставки, переполнение и восстановление через историю, замену локального instance, поздние результаты, занятый stdout, cancel и EOF. Для Windows действуют стабильные имена EXE и `scripts/run-cargo-tests-stable.ps1`. Этот проект ожидает отдельной приёмки до реализации.
