# T1.1e2b. Автоматические входящие в терминале

База `1adc98fd11246fa57a91f98751fec725c383e712`. [Контракт E2](terminal-t1-1e-contract.md) · [Проверки E2a](terminal-t1-1e2a-result.md)

На готовом Setup терминал наблюдает оба контекста после подтверждённого подключения owner или observer. Первый anchor задаёт границу старой истории. Follow открывает только новый диапазон, а reader использует штатный курсор E1 по страницам. Смена выбранного чата не влияет на наблюдение. Для каждого входящего события JSONL передаёт epoch, контекст и ID сообщения. TTY печатает номер чата и безопасное представление текста.

Чтение идёт через общий worker. Координатор выделяет резерв до чтения страницы. Подготовка, очередь и запись в полёте делят 64 места и 256 КиБ с двумя резервами для resync. При занятом бюджете чтение ждёт. Для страницы с сообщениями peer курсор меняется после своевременного write/flush последнего кадра. Пустая для вывода страница продвигается после проверки всех ordinal. Foreground-чтения, cancel и shutdown используют прежние барьеры E2a. Mutex не удерживается во время записи в stdout.

Обычный status показывает локальный monitor даже при отказе IPC. При потере непрерывности состояние resync и подтверждённые позиции сохраняются при disconnect/attach в том же процессе и контексте. Снять resync можно подтверждённым завершением новой полной цепочки явной истории, открытой после разрыва. Обычная история в исправном состоянии не продвигает курсор входящих.

## Проверки

- `build05` собрал CLI с `--locked --offline`, Cargo Idle и одним заданием. Проверки запускали стабильный `target/terminal-t1-checks/kilogram-cli.exe` с SHA-256 `9a1875c6631bf3b979f7e15c053db2bf70a68e66aa9e867ac0b7d232776c10cf`.
- `cli07` через стабильный CLI harness проверил справедливый допуск обоих контекстов, ограниченные повторы, `waiting_history`, `unsupported`, устаревший retirement и ACK, пределы вывода и экранирование. Прошли прежние проверки E2a для занятого writer, допуска чтений, командных ACK, отмены, ожидания TTY request ID и ограничений явной истории. Итого 23 теста. Вспомогательные сценарии с настройками через окружение проверяются в сквозном прогоне.
- `fixture03` подготовил свежую пару Setup. `smoke03` проверил CLI в режимах owner и observer, оба контекста, независимость от `/use`, TTY и JSONL на реальных локальных процессах. Начальная история observer не повторилась после anchor. Повторное подключение сохранило resync, старый курсор был отклонён. Прямые вызовы через аутентифицированный owner IPC подготовили 130 доставленных событий, пока observer держал открытый snapshot явной истории. После подтверждения последней страницы terminal получил весь накопленный диапазон по порядку и без дублей. Второй контекст восстановился отдельной цепочкой. В полном списке observer 133 уникальных ID, включая сообщение на 4096 байт с проверкой JSONL и TTY и сообщение после перезапуска peer.
- В `smoke03` harness подтвердил откладывание страницы при полном бюджете вывода, сохранение обеих позиций и отказ старой цепочке восстановления. После перезапуска peer новый обмен локаторами доставил сообщение из очереди при том же epoch observer. При остановленном IPC status вернул состояние monitor. `smoke03` завершился за 248,38 с, с кодами child и wrapper 0, EOF обоих потоков и пустым Job без принудительной уборки. Физический LAN относится к следующему этапу.

Квитанции и журналы сохранены в `.tmp/terminal-t1-1e2b/`. В `smoke01` драйвер запросил status после строки результата disconnect, до того как координатор завершил команду, и получил переходное состояние `session_closing`. В `smoke02` драйвер дождался подтверждения перехода и сквозной сценарий прошёл на предыдущей сборке. Финальная сборка добавила сохранение подтверждённых позиций при разрыве и дополнительную проверку просроченной цепочки явной истории.

После прерывания сессии три файла журналов `cli03` и `cli04` разошлись по хешу с исходными квитанциями. Состояние зафиксировано в `interruption-audit.json`. Повторная линковка `cli05` обнаружила повреждённый PDB с ошибкой LNK1285. Файл сохранён отдельно с хешем в `pdb-recovery.json`. `cli06` завершил тесты с кодом 0, но потребовал уборки дочернего процесса `vctip`. В `cli07` весь Job завершился штатно, включая EOF обоих потоков.
