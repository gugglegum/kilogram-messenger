## Assumptions checked before field

**Pending send and durable identity.** `runtime2/data.rs::queue` requires installed phase3/current policy, then performs a Local queue commit; `materialize` also commits locally without peer admission. Frontend `SessionSend::authorize` checks enabled context/phase3/policy/time without requiring a live peer lease. Thus the initial phase3 gate is required even with no initial texts. `send_recovery.rs::accept` removes the frontend's protected intent on materialized/delivered status, allowing the next context's request; queued/unconfirmed alone would leave `pending_request`. Adapter waits for materialized status and matching history before the next send. It never substitutes a new request ID after an uncertain result. This source review plus pure checks does not claim a new offline Rust execution or sender-crash durability test.

**Warm history/notification frontier.** A fresh Chat `Monitor::connect` creates a new context with no completed cursor. Its first read is `history_anchor` at the current tail, which emits no historical incoming notifications; only subsequent follow/page reads emit remote rows. Monitor attachment follows the acknowledged connect operation, so queued delivery can race the first anchor. No persistent notification cursor across a new Chat process is assumed.

Adapter requests warm `watching` immediately after B Connect and records recipient history before waiting for the full reconnect gate. If a queued event is absent then, its later exact notification is mandatory. If already present, delivered state/stable identity/history remain mandatory, while an absent notification is recorded **unproven_at_anchor**, not notification success and not an offline-delivery failure. A correctly captured notification confirms that event even at this boundary. Both online replies are always mandatory notification cases because A was watching. No artificial delay, hold, cursor reset or synthetic notification is introduced.

Delivery/history and notification coverage have separate verdicts. The adapter retains the existing bounded35s delivered wait and35s notification observation, accepts only `confirmed` or `not_observed`, and permits the latter only for an already-present queued event. It catches no transport, timeout, identity or arbitrary notification exception. After all normal cleanup/drains, it reconciles the complete observed set across all process incarnations: unexpected event, duplicate, wrong mailbox/runtime/epoch/context/text or a missing required event is a hard failure, including optional pre-anchor messages. Late duplicate events cannot escape the final check. `notifications-observed.json` preserves the full set, including hard-failure evidence.

`offline-recipient-result.json` schema2 separates `delivery_history.passed` from `notification_coverage`: required/observed/not_covered counts, per-message binding/coverage, required_passed and coverage_complete. Four delivered events with correct histories can pass this corrected scope with2 mandatory online notifications and2 explicitly unproven queued notifications. That is partial notification coverage, never universal notification success. When a queued event was absent at the boundary its later missing notification fails; neither history nor a blanket exception can replace it.

**Incarnation-bound cleanup.** Existing Diagnostic keeps one PID/snapshot/collected flag per host and the host reader caps a directory at16 files. B restart produces28 retained files, so neither array reuse nor silently skipping old files is safe. The adapter caches PID/runtime snapshot and collection state per `(host, tag)`, captures old B before restart, and stores separate `shutdown/B/owner-a-1` and `shutdown/B/owner-b-1` receipts.

The narrow reader extension accepts at most **one** exact previous `(Chat PID, runtime PID, instance)` scope. Default remains16 files; explicit two-incarnation read permits32 total, returning only current records (at most the original16) and `prior_validated` count. All files, including previous ones, still undergo name/size/reparse/schema/nonce/instance/PID validation. Unknown, malformed or wrong-scope files remain rejected; extra previous scopes/PID collisions/global overflow fail closed. No diagnostic file is removed, archived or rewritten.
