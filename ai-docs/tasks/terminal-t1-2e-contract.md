# T1.2e. Полевой прогон терминала от пустого каталога

База `8f82143bc6e92fd35342e82b91188f51f5e8146c`. Два Windows-хоста создают независимые Setup через штатный терминал, связываются по Direct LAN и подтверждают доставку в двух контекстах. Отдельный блок проверяет очередь при остановленном получателе и доставку после перезапуска. T1.1f уже проверил физический chat с подготовленными аккаунтами. D.2 уже проверил пустые каталоги, Setup → chat и живую доставку через loopback. Здесь проверяется их полный путь на двух физических хостах. ## Комплект и предпосылки

Перед повтором A/B транспорт управления терминалами сдаётся на отдельное review. Он использует короткие SSH-запросы поверх прежнего закреплённого ключа и локальный mailbox у владельца Job. [Контракт транспорта](terminal-t1-2e-mailbox.md)

- После приёмки использовать архивные CLI и bootstrap D.2 с SHA-256 `8c77c2e5cbfe2145b0cf3f8cc433204f90f99f60f6550eb79204c5395a3651f7` и `8ed2b27bf8a0e293e9622f58e5bc7999a9125b6ad8d573436f5455360fa112c8`. Сверять установленные файлы перед запуском на обоих хостах. Постоянные каталоги T1.1f — `E:\AI-Projects\kilogram-p2p-messenger\.tmp\terminal-t11f\bin` и `C:\Users\test\KilogramLab\terminal-t11f\bin`. Состояние хранить в новых локальных `runs/<attempt>/setup`. [Манифест образов](../../.tmp/terminal-t1-2d-2/build-images.json)
- Переиспользовать проверенные T1.1f Job-обёртку, pinned SSH/SFTP, `get/put` публичных файлов, наблюдение UDP, корреляцию JSONL и сверку истории. В драйвере заменить подготовительный вызов `t11f-fixture` на `setup --jsonl --dir <setup>`; добавить такой запуск в прежнюю host-обёртку. Для chat сохранить прежний запуск без PTY. Закрепить хеши драйвера, обёртки и deadline-скрипта в манифесте попытки. [Host](../../scripts/test-terminal-t1-1f-host.ps1) · [Контроллер](../../scripts/test-terminal-t1-1f-driver.py)
- На каждом хосте ключи хранятся с Windows DPAPI Current User. С момента создания child его stdin, stdout и stderr локально перенаправлены. Host-обёртка принимает только проекции разрешённых ответов. Она обрабатывает `recovery_show` на месте и в том же процессе Setup для одноразовых аккаунтов. После проверки ID и формы слов она выполняет `recovery_ack` и передаёт контроллеру безопасный результат. Исходные байты кадра в собственном буфере очищаются. Для строк JSON в управляемой памяти гарантии стирания нет. Это имитация сохранения слов для одноразовых аккаунтов. Долговременной копии и проверки восстановления здесь нет. Контроллер не может включить сквозную передачу приватных кадров. Базы, Root, слова, приватные журналы и IPC-дескрипторы остаются на своих хостах. [Recovery в терминале](terminal-t1-2a-contract.md)
- Перед запуском обновить read-only проверку пина, источника SSH, назначенных IPv4 с префиксами, категории конкретного LAN-интерфейса, действующей политики входящего UDP и динамического диапазона. Результат относится к текущим интерфейсу и пути EXE. При включённом firewall нужен уже действующий допуск для этого пути, пары адресов и новых UDP-портов. Ранее наблюдавшиеся порты не служат разрешением. При неподтверждённых предпосылках полевой запуск остаётся на паузе. Firewall, сеть и системные настройки в этом срезе не меняются. ## A. Создание и короткий живой обмен

1. На ПК `begin/create`, локальная операция recovery, `invite_export`. На ноутбуке `invite_inspect/invite_join` по показанному preview ID с явным подтверждением, `create`, локальная операция recovery и `reply_export`. На ПК `reply_inspect/reply_accept`. Сверить публичные account/device обоих хостов, invitation и два упорядоченных контекста по независимо подтверждённым результатам каждого Setup. Передавать только артефакты данной попытки с проверкой типа и SHA-256.
2. Выбрать роли по каноническому порядку device ID. Proposer передаёт proposal, cosigner явно подтверждает просмотренный snapshot, подписывает и возвращает final. Proposer подтверждает просмотренный final. Оба выполняют `consent_import` с двумя `accepted`. Сохранить зеркальные `route_lan` для подтверждённых адресов и проверить public status с маршрутом и `profile_state:not_prepared`. Выполнить `quit` и дождаться фактического освобождения Setup lock. [Согласие](terminal-t1-2c-contract.md) · [Маршрут](terminal-t1-2d-contract.md)
3. На обоих хостах запустить `chat --setup <setup> --jsonl` и `connect {"mode":"start"}`. До обмена локаторами проверить локальный owner/IPC instance и `live_admitted:false`. Для каждого owner связать Job, текущий `runtime_instance`, реально привязанный IPv4:UDP и опубликованный подписанный socket двух локаторов. Импортировать свежие bundles. Дождаться `live_admitted:true` с `watching` для обоих контекстов на обоих хостах.
4. Из исходно пустой истории отправить одно сообщение в первом контексте с ПК и одно во втором с ноутбука. Для каждого сохранить уникальный `request_id`, delivered event ID, ровно один входящий event у получателя с теми же контекстом, текстом, instance и monitor epoch, и полную совпадающую строку истории по обе стороны. Сохранить зачёт A до перехода к B.

## B. Очередь и перезапуск получателя

1. Штатно остановить owner ноутбука. Подтвердить exit, EOF, пустой Job и исчезновение его дескриптора. На ПК отправить одно сообщение с новым `request_id` в выбранном контексте. Записать `queued` или `materialized` через `request_status` до запуска получателя.
2. Открыть тот же Setup ноутбука. Сверить прежние public pins и новый `runtime_instance`. Сначала дождаться `watching` на сохранённой истории. Затем оба owner обмениваются свежими локаторами. Записать фактический порт нового runtime и рост ревизий локаторов получателя. Повторное выделение того же номера порта допустимо. Снова подтвердить живой допуск обоих слотов.
3. Дождаться `delivered` для сохранённого request ID. Проверить ровно один входящий event у нового instance получателя и по одной строке этого события в обеих историях. `retry` с тем же ID возвращает тот же event ID. Сверить итоговое точное множество из трёх событий на каждом хосте, включая ID, текст, контекст, роль и ordinal. В итоговом журнале получателя ни повторной строки, ни второго уведомления для этого события.
4. Оба owner завершить через `quit`. Подтвердить штатные коды child и wrapper, EOF обоих потоков, пустые собственные Jobs и отсутствие обоих IPC-дескрипторов. При тайм-ауте сохранить уже полученные квитанции, публичные артефакты и состояние. Применять только ограниченное завершение собственных процессов. Принудительная уборка не засчитывается как штатная.

Контроллер фиксирует A и B отдельными квитанциями. Плановые пределы A — 450 с, B — 250 с, с отдельным резервом 30 с на уборку. Chat owner, переживающий границу A и B, использует весь оставшийся сценарий до уборки. Job этого процесса сохраняет собственный абсолютный предел 760/790 с от запуска, setup Job использует 450/480 с. При диагностическом перерыве B можно начать с обоих закрытых Setup из зачтённого A, сверив историю, те же привязки, образы и свежие локаторы владельцев. Уже записанный offline-запрос восстанавливают по исходному ID и состоянию очереди.

Доставка, повтор по исходному ID и точная история фиксируются в `phase-b-delivery.json` отдельно от уведомлений. Драйвер ждёт incoming и при доставке до свежего обмена. Момент доставки сам по себе не определяет, попало ли событие в исходную историю монитора. После EOF драйвер повторно проверяет ровно одно уведомление для каждого события по всем наблюдавшимся сеансам. При отсутствии уведомления сохраняется подтверждённый результат доставки, а полный B остаётся непроверенным. Повторять A из-за этого не требуется.

## Квитанции и граница сдачи

Привязать каждый setup/chat процесс к ожидаемому hostname, способу запуска, хешам EXE, tag и Job. В сводке сохранить public account/device, invitation, упорядоченные context IDs, хеши публичных передач и времена ключевых шагов. Для всех chat-поколений сохранить runtime instance, PID и наблюдаемый UDP socket, ревизии, live/monitor status, request/event IDs и историю. Протокол A должен быть читаем и при отказе B. [Схема свидетельств T1.1f](terminal-t1-1f-plan.md)

Используются существующий протокол, E2EE, DPAPI, terminal setup и chat. Синтетическая проверка проходит до обработки настоящих recovery-ответов. Полевой комплект и результат предъявляются архитектору вместе со сквозными A/B-квитанциями после проверки обоих хостов.
