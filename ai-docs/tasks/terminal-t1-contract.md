## T1.0 — квалификация Windows и SSH

Ранее `CryptProtectData` в прямом OpenSSH network logon возвращал Windows error 5. Новый logon того же тестового пользователя через `Start-Process -Credential -LoadUserProfile` позволил создать аккаунт с `windows-dpapi-current-user`. Требуется заново проверить открытие существующего тестового состояния, protected send и управление процессом. PTY влияет на ввод и вывод; контекст DPAPI квалифицируется отдельно. [Журнал окружения](../development-environment.md#L3151) · [DPAPI state key](../../crates/kilogram-state/src/key_provider.rs#L250) · [DPAPI send intent](../../crates/kilogram-first-dialog/src/send_intent.rs#L339)

### T1.0a — DPAPI и stdio на одноразовых данных

В локальном пользовательском запуске выполнить current-user protect случайных байтов и unprotect в другом процессе, отдельно измерив тип logon. В обычном SSH без PTY проверить такую же пару и, если доступен локальный контроль того же пользователя на том же хосте, перекрёстное чтение его пробы. Наблюдать UTF-8 JSON через stdin/stdout, EOF и exit code на безвредном echo. В доказательства входят стадии, код Win32, длительность, контекст logon и признаки совпадения. Байты пробы и DPAPI blob остаются в одноразовом каталоге. Аккаунты появятся только после результата этого блока. DPAPI, парольные logon и политики ОС исключены из изменений. [Инструмент](../../scripts/test-terminal-t1-dpapi.ps1)

### T1.0b — проверка runtime после результата T1.0a

На свежем одноразовом Setup/Profile2 использовать `runtime-from-profile` и `ordered status2/history2`. Зафиксировать стабильный абсолютный путь и хеш тестового EXE, local IPv4 и проверенный SSH host key. При работающем в локальном сеансе runtime из SSH выполнить status и чтение тестовой истории. Descriptor остаётся локально и содержит bearer token. Типизированным `Client2` проверить отказ при неверном identity или устаревшем descriptor. Отдельно выполнить холодный старт из квалифицированного logon, подтвердить открытие защищённого состояния, новый `runtime_instance`, stop с reaping и удалением собственного descriptor, затем restart. Перед сдачей T1.1 подтвердить запись и открытие штатного pending intent тем же owner до первого IPC send. Дедлайны — 10 с для IPC-наблюдения, 45 с для старта, 30 с для cleanup. [Descriptor](../../crates/kilogram-runtime-ipc/src/lib.rs#L472) · [Owner startup](../../crates/kilogram-first-dialog/src/connection.rs#L484)

Read-only `ssh-attach` — частичный результат. Если direct SSH не обеспечивает DPAPI, отдельный вариант для архитектурной проверки — явно запущенный пользователем owner в его локальном сеансе и аутентифицированный адаптер команд, доступный через SSH. Durable send intent выполняет тот же owner в своём сеансе. Службы, scheduled tasks, автозапуск, хранилище credentials и сетевой admin listener в этот вариант не входят.

До LAN-проверки подтвердить private interface, адреса local/peer, разрешение входящего UDP для стабильного EXE и ожидаемого тестового диапазона портов. После restart проверить фактический порт и новую ревизию локатора, обменяться публичными envelopes и подтвердить живой допуск обоих слотов. Если подготовленное правило не подходит, остановить сетевой тест и сообщить о предпосылке. Terminal не меняет firewall или профиль сети. Сетевые Rust harnesses на Windows компилировать без запуска, запускать через `scripts/run-cargo-tests-stable.ps1`. Для компиляции использовать Idle/Jobs1.

## T1.1 — первый исполнимый терминальный срез

**Владение.** `connect(start)` открывает готовый Setup, использует сохранённый профиль и LAN-маршрут, выполняет штатную проверку consent и запускает один собственный runtime. В этом режиме доступны отправка и locator import/export. `connect(attach)` сверяет descriptor с account/device/contexts из локального Setup/Profile2 и закрепляет текущий instance через status. Наблюдатель читает публичные привязки без захвата пишущего Setup и без открытия устройства или DB. После устаревшего descriptor нужен повторный attach к заново проверенному instance. `disconnect` у владельца означает shutdown с подтверждённым exit/EOF/reap и проверкой удаления descriptor. Наблюдатель только отсоединяется. Второй владелец того же Setup или state-dir получает отказ. До подтверждения cleanup ещё один старт запрещён. Подписи, ограничения пути, expiry, проверка обоих слотов и формат состояния остаются в прежних валидаторах.

**Команды.** `/help`, `/connect start|attach`, `/status [request_id]`, `/chats`, `/use 1|2`, `/send <текст>`, `/history [limit]` и `/history more`, `/retry <request_id>`, `/locator export`, `/locator import <путь>`, `/cancel`, `/disconnect`, `/quit`. `/chats` показывает два закреплённых диалога, начальный выбор — 1. Обычная строка отправляется в выбранный диалог. Начальное `//` экранирует один `/`. Неизвестная slash-команда возвращает ошибку. Текст и хвост пути не интерпретируются оболочкой. В TTY одна строка — одно сообщение. JSONL поддерживает многострочный текст как строку с экранированными переводами строки. Общий лимит — 1–4096 байт UTF-8. Терминальный вывод экранирует управляющие символы.

**Отправка и восстановление.** Сохранить одну DPAPI-защищённую незавершённую отправку на Setup с существующими привязками setup/account/device/claim/peer/context, точными текстом и request ID. TTY показывает сгенерированный 128-битный ID до попытки отправить. JSONL передаёт заранее выбранный ID из 32 hex-символов. Общий `Recovery` принимает этот ID. Новое намерение возможно после проверки отсутствия соответствующего запроса в runtime и незавершённой записи. Файл публикуется и перечитывается до IPC. Если receipt потерян, сначала проверить `request_status`. `retry` после проверки статуса повторяет сохранённые точные ID и текст. Уже известный ID направляет к status, конфликт с сохранённым текстом или контекстом даёт отказ. Найденный runtime receipt не подтверждает произвольно повторно поданный текст. Если ранее подтверждённая запись исчезла, сохранить блокировку и прогресс. Различать `protected`, `queued`, `materialized`, `delivered` и `unconfirmed`. Недоступность peer допускает штатную очередь при действующих локальных условиях. Для `queued` требуется подтверждение собственного runtime. [Store](../../crates/kilogram-first-dialog/src/send_intent.rs#L176) · [Повтор и receipt](../../crates/kilogram-first-dialog/src/send_recovery.rs#L184) · [Idempotency Owner2](../../apps/kilogram-cli/src/ordered_dialog/runtime2/data.rs#L298)

**История и входящие.** Использовать `Client2::history_page` и непрозрачный continuation handle с привязкой к сессии, контексту и snapshot. Для короткого пилота получать начальную страницу примерно раз в секунду и при изменении frontier проверять новый snapshot целиком. Бюджет фонового прохода на контекст — до 128 строк, 256 КиБ кодированных страниц и 5 с wall time, по первому достигнутому пределу. Этот бюджет ограничивает фоновый просмотр, явная история остаётся постраничной, объём сохранённой переписки этим контрактом не ограничивается. В первом полном проходе установить watermark без повторного вывода старого. Далее выдавать новые строки peer обоих контекстов с дедупликацией по (context, event). Watermark продвигается после полного подтверждённого прохода и успешной постановки всей пачки уведомлений.

При потере позиции, истечении бюджета, ошибке cursor или переполнении очереди уведомлений сохранить прежний watermark и выставить `resync_required` для этого контекста. Признак хранится отдельно от очереди и доступен из `status`, уведомление передаётся при восстановлении вывода. Очередь не задерживает send/cancel/cleanup. Позицию восстанавливает явная история с завершённым snapshot. Общий IPC умеет `WaitForChange`, Fresh runtime2 сейчас не публикует change counter. Выбор incremental API — следующий срез без изменений хранилища в T1.1. [Пагинация](../../crates/kilogram-state/src/vault/indexed_dialog/history.rs#L164) · [IPC change counter](../../crates/kilogram-runtime-ipc/src/lib.rs#L2044)

**JSONL и завершение.** UTF-8 без BOM, LF или CRLF на входе, максимум 32 КиБ на строку. JSONL без PTY. Протокол v1 принимает `{v,id,op,args}`. `id` только коррелирует команду в сессии, `request_id` принадлежит защищённой отправке и переживает reconnect. При работающем stdout у принятой команды ровно один `result` с её `id` и `ok`/кодом ошибки. Дубль активного `id` не исполняется: сообщение об ошибке строки использует отдельный тип, сохраняя однозначность результата исходной команды. Ответы send/retry/request status несут `request_id` и контекст. Событие содержит вид, `runtime_instance`, контекст и `event_id`, если он известен. Stdout содержит ответы и события, stderr — краткие диагностические коды без содержимого.

Один изменяющий запрос за раз. Ограничить выход буфером до 64 уведомлений и 256 КиБ, отдельно резервировать место для ответов принятых команд. При backpressure остановить приём новых действий с побочными эффектами, сохранить управление cancel/cleanup и сигнализировать потерю уведомлений через resync. Невалидная строка не вызывает операцию. `cancel` по ID активной команды или Ctrl+C запрашивает отмену. EOF, broken stdout и `quit` прекращают приём и запускают ограниченное завершение. Наблюдатель отсоединяется, owner закрывает свой runtime. Запись может пережить обрыв канала или отмену. При неизвестном исходе send после нового подключения использовать тот же `request_id` в `request_status`. Код 0 — штатное завершение, 2 — фатальная ошибка запуска/потока, 3 — неподтверждённый cleanup. Ошибки отдельных операций проверяются по `result`.

Wire-операции соответствуют командам: `connect(mode)`, `status`, `chats`, `send(context,request_id,text)`, `request_status(context,request_id)`, `retry(context,request_id)`, `history(context,limit,cursor?)`, `locator_export`, `locator_import(path)`, `cancel(target_id)`, `disconnect`, `quit`. JSONL выбирает контекст явно по ID из `chats`, поэтому `use` и `help` остаются интерфейсом TTY. `ready` сообщает о запуске обработчика команд, результат `connect` — о локальной готовности runtime, а live admission наблюдается отдельно. Перед дальнейшими действиями драйвер проверяет соответствующие result/event, а не ждёт наугад по таймеру.

Для явной истории лимит вывода применяется после экранирования с учётом оболочки result и завершающего перевода строки. При превышении возвращается `response_too_large` с исходным correlation ID. Повтор запрашивает ту же позицию с меньшим `limit` или через `/history more <limit>`. Позиция продвигается после отправки полной страницы. Завершённый correlation ID освобождается непосредственно перед записью ответа, пока вывод ещё упорядочен. Во время записи и flush блокировка ID свободна.

T1.1a поддерживает штатное завершение через EOF, `/quit` и обнаруженный отказ stdout. `cancel` и обработка Ctrl+C в этом срезе отсутствуют и не проходили проверку. Реализация и проверка обоих путей обязательны для приёмки полного T1.1.

| Приёмка T1.1 | Проверяемое наблюдение |
| --- | --- |
| Два физических хоста, SSH без PTY там, где квалифицирован owner | Тот же Setup entry point в TTY и pipe. Аутентификация двух слотов, сообщение и ответ, входящее событие с тем же event ID, что и в истории. Ручной запуск отмечается отдельно. |
| Offline и restart | Получатель остановлен, отправитель сохранил запрос с известным ID. После restart получателя и обмена актуальными локаторами сообщение доставлено ровно один раз. Истории двух контекстов раздельны. |
| Потерянный ответ и восстановление отправителя | Имитировать потерю ответа после защиты намерения и после принятия runtime. После запуска status/retry с тем же ID дают один request/event и одну запись у peer. Подмена текста или контекста отклоняется. |
| Ошибки и закрытие | Неверный descriptor/контекст, повреждённая JSONL, cancel до и после сохранения, EOF в owner и attach. Предложенные дедлайны драйвера — 10 с на обычный result, 45 с на start/ready, 60 с на событие доставки после готовности LAN, 30 с на cleanup. Timeout сохраняет request ID и наблюдаемое состояние. |

Следующий срез переносит создание аккаунта, invite/reply, независимую сверку идентичности, consent и настройку LAN над теми же сервисами. Он даёт путь от пустой установки. Telegram-подобный GUI остаётся отдельным frontend, предложение CS4.1c сохранено. Будущий MCP может стать отдельным локальным stdio-адаптером тех же операций и подтверждений. Сетевой admin listener, выдача приватных ключей и слов восстановления вне его границ. Headless/MCP-проверки покрывают сервис и обмен. Ввод, отрисовка и отзывчивость GUI требуют собственных проверок.
