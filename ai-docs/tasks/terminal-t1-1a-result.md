# T1.1a — терминальный просмотр готового Windows Setup

База `5617f277e325efebc4905ebd8dbba982f9805928`. Контракт [T1](terminal-t1-contract.md).

## Границы до реализации

- Открыть готовый Setup по `kilogram-cli chat --setup …`. Перенести headless код первого диалога в библиотеку приложения. GUI сохраняет тот же worker, те же форматы, проверки согласия и защищённую отправку. Терминал использует штатный worker для владения процессом и типизированный `Client2` для read-only attach.
- TTY и JSONL используют те же команды, кроме выбора текущего контекста и справки в TTY. Владелец штатно останавливает свой runtime при выходе, EOF или проблеме stdout. Наблюдатель только отсоединяется. Продолжение истории связано с текущим подключением, контекстом и курсором снимка.
- Текст, отправка, повтор, входящие события и обмен локаторами отложены. Терминальный API этого среза предоставляет только чтение и жизненный цикл.
- Проверка на свежих Setup с DPAPI: framing и ошибки UTF-8, оба frontend, один owner и независимый observer, ошибка identity и смена descriptor, страницы обоих контекстов, shutdown при quit, EOF и отказе stdout. Сначала основной ПК, затем pinned SSH без PTY при наличии ноутбука. Сетевые тесты выполняются через стабильный Windows runner, Idle/Jobs1. Полевые аккаунты CS4 и системные настройки исключены.

## Работа с готовым Setup

`kilogram-cli chat --setup <каталог>` открывает консоль, `--jsonl` включает машинный поток UTF-8. Команды `/connect start` и `/connect attach` соответственно запускают одного владельца и открывают наблюдение. `/status`, `/chats`, `/use 1|2`, `/history [limit]`, `/history more`, `/disconnect` и `/quit` работают над теми же локальными операциями. В JSONL поле `context` должно содержать ID выбранного диалога, а `cursor` берётся из предыдущей страницы той же сессии и контекста. Сообщения из истории экранируются при терминальном отображении. Список операций доступен через `/help`.

Код Windows Setup, свежего consent, локального процесса и защищённой отправки GUI перенесён в `kilogram-first-dialog` без изменений форматов. Обе оболочки используют `connection::Work`. Локальный наблюдатель читает ожидаемые account/device/contexts из Setup и профиль с сохранённым digest. Дескриптор закрепляется после проверки подписанной структуры и идентичности в `Client2`, затем проверяются instance и маршрут. Наблюдатель не захватывает lock Setup. Он не пишет состояние и не отправляет shutdown. [Общий сервис](../../crates/kilogram-first-dialog/src/chat.rs) · [Терминальный вход](../../apps/kilogram-cli/src/terminal_chat.rs)

Вход ограничен 32 КиБ на строку, запись результата ограничена 256 КиБ и 3 с ожидания подтверждения записи. Вход без завершающего LF читается до EOF. Повтор активного correlation ID выдаёт отдельную ошибку строки. Ни slash-команды, ни данные JSONL не передаются оболочке. У владельца EOF, quit и сбой записи вызывают штатную остановку; неподтверждённое завершение блокирует новый старт в том же сеансе. При закрытом или недоступном stdout подтверждение на нём может отсутствовать. Ошибка stdout обнаруживается при записи, а работа истории и runtime отделена от потока записи.

## Свидетельства

Локальный `frontend01` прошёл на синтетической DPAPI-паре. JSONL вернул две страницы первого контекста и отдельную историю второго. Чужое продолжение и второй owner отклонены. Независимый observer прочитал те же данные, а его quit сохранил владельца. TTY подтвердил Unicode и экранирование ESC. EOF, закрытый reader stdout и заполненный stdout без reader привели к освобождению runtime. При отказе stdout ожидаемый код CLI был 2. Квитанции `frontend01.receipt.json` и `frontend-evidence01.json` сохранены в `.tmp/terminal-t1-1a`.

Сборочный toolchain Windows работал с одним заданием и приоритетом Idle. Первый отдельный тест общего сервиса остановился на пропущенном поле в тестовом инициализаторе. В `fixture02`, `gui01` и `parser01` сами тесты прошли. Обёртка каждого прогона вернула код 1 из-за оставшегося процесса `vctip`, который был завершён внутри тестового Job Object. Исходные квитанции сохранены.

Повтор `regress01` на новой паре прошёл с кодами child/owner 0, EOF и пустым Job Object. Через стабильный Windows runner выполнены три выбранных теста: GUI cancel и очистка слов восстановления, проверка привязок observer и страниц истории, отбрасывание позднего статуса общего worker. Observer отверг подписанный descriptor другого аккаунта, неверный ожидаемый instance и обращение к остановленному runtime.

`parser02` подтвердил три CLI-теста framing, UTF‑8, согласованности slash/JSONL, отказа в отправке и защиты активного correlation ID. Коды 0, EOF и пустой Job Object. CLI и Windows GUI собраны с `--locked --offline`. Финальный `lockedcheck01` повторно проверил CLI, GUI и общую библиотеку с итоговым lockfile. После переноса для CS3.2b и других headless тестов первого диалога используется пакет `kilogram-first-dialog`. [Обновлённый рецепт CS3.2b](clean-start-cs3-2b-connection-recipe.md)

Через прямой pinned SSH без PTY на ноутбуке проверен тот же CLI SHA‑256 `2d79254200271f267f97c4afe10152d22ba56118b64801547156cb2db2ceee60`. В новом каталоге `C:/Users/test/KilogramLab/terminal-t1-1a-a01` инструмент создал два DPAPI Setup на месте через штатные bootstrap и consent. Два owner и observer работали через loopback. JSONL owner и observer вернули одинаковые завершённые страницы для обоих контекстов. Quit наблюдателя не закрыл владельца. EOF и quit владельцев вернули код 0 и удалили дескрипторы. ## Исправления после R1

Ограничение 256 КиБ учитывает полный результат после экранирования, включая JSONL-оболочку и перевод строки. При переполнении терминал возвращает `response_too_large` и сохраняет прежнюю позицию истории. JSONL сохраняет исходный ID в ответе. Для повтора используются тот же cursor и меньший `limit`, в TTY также доступна команда `/history more <limit>`.

ID освобождается потоком записи перед выдачей первого байта завершённого ответа. При выполнении команды повтор активного ID по-прежнему отклоняется. Запись и flush идут без блокировки набора ID, а подтверждение старой записи больше не обращается к набору.

`cancel` и обработка Ctrl+C отсутствуют в T1.1a и не проверялись. Их реализация и проверка остаются обязательными для полной T1.1. Квитанции полной исходной проверки GUI и ноутбука относятся к предыдущему EXE.

Сборка R1 `build02` с `--locked --offline`, приоритетом Idle и одним заданием дала CLI с SHA‑256 `d0ebe6cf43b797d3801fa0f3365f4d3282d0f0028d87f3fa65c9c14feae0e8af`. Стабильный Windows runner в `parser02` подтвердил шесть CLI-тестов. Синтетические страницы проверили лимит после экранирования в TTY и JSONL, повтор с меньшим лимитом и выдачу всех строк по порядку. Отдельный тест подтвердил освобождение ID перед записью и сохранение следующего резервирования.

Локальный `smoke01` на этом EXE вернул 12 000 ответов на 12 000 последовательных запросов с одним ID. На тестовых Setup прошли пять проверок: история, пагинация и quit владельца и наблюдателя через JSONL, та же история и экранирование через TTY, освобождение владельца при EOF, обрыве и остановке чтения stdout. У `build02`, `parser02` и `smoke01` коды child/owner равны 0, зафиксирован EOF, Job Object пуст без принудительной очистки. Первые `build01` и `parser01` завершили свои команды с кодом 0, но обёртке пришлось завершить оставшийся `vctip`. Исходные квитанции, чистые повторы и архив заменённых CLI harnesses сохранены в `.tmp/terminal-t1-1a-r1`.
