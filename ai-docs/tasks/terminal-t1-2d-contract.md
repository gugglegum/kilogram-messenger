# T1.2d. Маршрут LAN и переход из Setup в chat

База `27b8d0315f37652b654ba2b11cf1216588528fd0`. Два владельца создают отдельные Setup штатными командами T1.2a–c, подтверждают личности и согласие, сохраняют на каждом устройстве свой маршрут и выходят из `setup`. Дальше используют действующий `kilogram-cli chat --setup <dir>`. Setup остаётся локальным с Windows DPAPI. У каждого владельца один runtime для обоих контекстов. [Контракт согласия](terminal-t1-2c-contract.md) · [Границы терминального пилота](terminal-t1-contract.md)

В D.1 реализована защита от повторного старта после неподтверждённой уборки helper до запуска runtime. Команды маршрута, публичный статус профиля и сквозной сценарий Setup → chat остаются проектом D.2.

## Команды и сохранённое состояние

| TTY в `setup` | JSONL `op` и `args` | Результат |
| --- | --- | --- |
| `/route lan <local_ipv4> <peer_ipv4>` | `route_lan {"local_ipv4":"192.168.1.10","peer_ipv4":"192.168.1.11"}` | Снимок Setup с явно сохранённым Direct LAN. На другом устройстве адреса меняются местами. |
| `/route loopback` | `route_loopback {}` | Снимок Setup с локальным маршрутом `127.0.0.1:0`. Это также действующее значение по умолчанию у старого Setup без LAN. |

Обе команды исполняет имеющийся worker под Setup lock. Нужны готовый аккаунт, сохранённые слова, выбранный peer и сохранённый final для обоих контекстов. `refresh_terminal` уже проверяет durable ссылки и подписи. Выбор адресов возможен после повторного открытия Setup и не требует заново подтверждать локальный импорт. Текущая действительность согласия и установка проверяются при старте chat. Формат JSONL v1 и поведение при занятости остаются теми же. [Worker Setup](../../apps/kilogram-cli/src/terminal_setup/service.rs#L93) · [Проверка при открытии](../../crates/kilogram-first-dialog/src/model.rs#L277) · [Предпосылки Windows GUI](../../apps/kilogram-windows/src/fresh_onboarding/mod.rs#L578)

В успешном ответе и при `open/status` готового Setup добавить `connection={mode,local_ipv4,peer_ipv4,profile_state}`. `mode` принимает `direct_lan` или `loopback`. Для loopback вывести `local_ipv4:"127.0.0.1"` и `peer_ipv4:null`. Прочитать сохранённые адреса через `connection::lan_settings`. Снимок отражает сохранённый выбор. Проверку назначения адреса выполняют команда выбора и runtime, а не каждый `status`.

- `profile_state:"not_prepared"` если дайджест ещё не сохранён и файл отсутствует. Точный файл после прерванной записи также ожидает фиксации дайджеста в `prepare`.
- `profile_state:"prepared"` означает проверенный текущий `Profile2Document`. Для этого read-only сверка проверяет безопасный путь, совпадение сохранённого дайджеста и полное равенство ожидаемому документу. Действительность согласия и живая связь проверяются отдельно. Вынести узкую общую проверку из `Observer::open`, чтобы `open/status` использовали те же правила. Для снимка worker не создаёт каталог. Координатор отвечает последним снимком без параллельного чтения.
- `profile_state:"conflict"` при сохранённом дайджесте без соответствующего имени или файла, небезопасном пути либо несовместимом существующем файле даже без дайджеста. Показывается как проблема профиля с сохранённым выбором маршрута. Для нового запуска нужны доступные и проверенные локальные артефакты.

Поле `consent` сохраняет семантику T1.2c. В Setup нет статуса живого подключения. TTY показывает режим, адреса и состояние профиля и предлагает `/quit`, затем отдельный запуск `chat --setup`. Снимок не выводит claim, пути к приватному состоянию, ключи, слова или IPC descriptor. ## Проверка и применение маршрута

- Парсить только два IPv4 без порта, CIDR или DNS. Использовать `LanSettings` и `DirectLan2::new` для двух разных private IPv4. В библиотеке CLI открыть один вызов поверх работающего `runtime2::lan::verify_interface` для Windows Setup. Он проверяет однозначно назначенный **локальный** IPv4 и его реальный префикс. `DirectLan2::check_on_link` требует префикс 1–30 и оба адреса в одной сети. Адрес сети, directed broadcast и off-link peer отклоняются. Доступность удалённого устройства и его идентичность устанавливает существующий обмен локаторами и admission. [Windows-валидатор](../../apps/kilogram-cli/src/ordered_dialog/runtime2/lan.rs#L5) · [Правила адресов](../../crates/kilogram-protocol/src/ordered_dialog_v2/runtime_locator.rs#L12)
- После preflight применить существующий `connection::select_route` через узкий публичный вызов для остановленного Setup. Совпадающий маршрут не переписывает `setup.json`. Смена маршрута атомарно сохраняет `connection.lan`, сбрасывает ссылки на профиль, результаты импорта **локаторов** и последнее состояние запуска. Прежние файлы профиля и локаторов, ссылки на удержанный вход и сами разрешения остаются в исходном виде по правилам `select_route`. При новом маршруте проверка удержанного локатора повторно сверяет его с актуальной route и runtime. Возврат к loopback требует явной команды. [Сохранение маршрута](../../crates/kilogram-first-dialog/src/connection.rs#L110) · [Повтор проверки локатора](../../crates/kilogram-first-dialog/src/connection/locators.rs#L163)
- До записи маршрута проверить известные цели под `connection` и их предков действующим `validate_artifact_path`, включая ожидаемые типы для каталога `connection/locators`, IPC-файла и текущего профиля. Отсутствующие цели допустимы. Никогда не заменять или удалять существующие файлы в этих командах. `prepare` при chat сам создаёт отдельное случайное имя, запрашивает no-clobber-запись и сверяет итоговый документ и digest. Защиту пути применить до первого создания каталога и перед использованием записанного профиля. Подмена байтов, junction/reparse и выход из каталога Setup отклоняются. Для смены маршрута старый обычный профиль остаётся на диске. [Guard артефактов](../../crates/kilogram-first-dialog/src/connection.rs#L147) · [Prepare](../../crates/kilogram-first-dialog/src/connection.rs#L213) · [No-clobber запись](../../apps/kilogram-cli/src/ordered_dialog/admin.rs#L186)

Ошибки Setup используют обычный ответ `ok:false,code`. Форма запроса или IPv4 дают `invalid_args`, одинаковые либо непригодные private адреса дают `invalid_lan_route`, отказ проверки назначения или префикса даёт `lan_interface_unavailable`. Готовность и lock дают действующие `not_open`, `invalid_state`, `recovery_required`, `peer_required`, `setup_locked` или `busy`; отсутствие final даёт `consent_not_ready`. Небезопасная цель даёт `connection_path_invalid`, ошибка записи даёт `route_save_failed`. Ошибка проверки сохраняет прежний выбор. При потерянном ответе открыть Setup и посмотреть маршрут, та же команда безопасна для повтора. Диагностика chat сохраняет существующий публичный `connect_failed` для отказа запуска и сообщения locator API для отказа обмена.

## Переход к общению

1. Выполнить `/quit` или `quit {}` и дождаться штатного выхода процесса. Ответ `closed:true` выдаётся после выхода worker. Он держит `Setup` и освобождает `.onboarding.lock` при выходе. Закрытие без ACK требует дождаться фактического завершения процесса. Chat owner, запущенный до освобождения lock, получает отказ. Единый Setup lock используют также GUI и owner. [Закрытие Setup](../../apps/kilogram-cli/src/terminal_setup.rs#L405) · [Setup lock](../../crates/kilogram-first-dialog/src/model.rs#L133) · [Guard terminal Setup](../../crates/kilogram-first-dialog/src/model/terminal.rs#L64)
2. Запустить `kilogram-cli chat --setup <тот же dir>` с `--jsonl` при необходимости. Отдать `/connect start` или `connect {"mode":"start"}`. Действующий `Chat::connect_controlled` снова открывает Setup и передаёт сохранённый маршрут в `Work::start_terminal`. `prepare` заново предъявляет оба final локальному репозиторию, проверяет строгий интервал `not_before <= now < expires_at` и готовит или повторно проверяет Profile2. Ожидаемый документ закрепляет account/claim/device, два контекста и `enabled=[0,1]`. Собственный `runtime-from-profile` получает state-directory lease. Для LAN используется `FreshRoute2` с `direct-only`, одним concrete bind `local_ipv4:0`, `lan_peer_ipv4` и без relay, lookup или port mapping. IPC слушает loopback. Runtime повторяет проверку реального интерфейса перед открытием базы и периодически после запуска. Потеря назначенного IPv4 не включает другой маршрут. [Путь owner](../../crates/kilogram-first-dialog/src/chat.rs#L109) · [Runtime и lease](../../apps/kilogram-cli/src/ordered_dialog/runtime2/runtime.rs#L996) · [FreshRoute2](../../crates/kilogram-transport-iroh/src/ordered2.rs#L40) · [IPC](../../crates/kilogram-runtime-ipc/src/lib.rs#L2002)
3. Оба owner выполняют существующие `/locator export`, `/locator import <путь>` или JSONL `locator_export {}`, `locator_import {"path":"..."}`. Передавать только свежий публичный envelope из нужного runtime. Входящий envelope сверяется с выбранным peer и с двумя контекстами. Подписи, интервал, ревизии, один endpoint и один подписанный LAN socket на оба слота проверяются существующими валидаторами. Порт берётся из фактически привязанного UDP socket. После restart обменять заново. При частичном импорте `/locator retry` повторно проверяет сохранённый точный документ. [Валидация envelope](../../crates/kilogram-first-dialog/src/locator_artifact.rs#L103) · [Экспорт и импорт](../../crates/kilogram-first-dialog/src/connection/locators.rs#L121)
4. `connect start` и `status.connected` подтверждают локальный IPC instance. Для результата связи требовать `status.live_admitted` у обоих owner. Он требует свежего наблюдения и двух активных допущенных слотов с актуальными согласиями, lease и проверенным LAN path. После этого использовать существующие `/use 1|2`, `/send`, `/history` или действующие JSONL команды и сверять доставку. При `disconnect/quit` chat завершает только свой runtime и подтверждает exit, EOF и исчезновение собственного descriptor до успешного возврата. Setup не запускает процессы chat и не передаёт открытый lock. [Публичный status chat](../../apps/kilogram-cli/src/terminal_chat.rs#L405) · [Текущий допуск](../../crates/kilogram-first-dialog/src/connection.rs#L453) · [Проверки двух слотов](../../crates/kilogram-first-dialog/src/connection.rs#L749) · [Остановка owner](../../crates/kilogram-first-dialog/src/chat.rs#L339)

### Защита D.1 до запуска runtime

`prepare` принимает точный файл после обычной ошибки helper с подтверждённым завершением. `Cancelled` и `CleanupUnconfirmed` останавливают подготовку до принятия файла. Ошибка неподтверждённой уборки от любого из двух helper сохраняется в результате и в возвращённом объекте Setup. При передаче Setup из завершившегося `Work` новый `Work` отклоняется. GUI сохраняет этот Setup и блокирует действия в текущем окне. Chat учитывает флаг до проверки `!spawned()`, отклоняет повторный connect и возвращает неуспех закрытия через существующий ограниченный shutdown. Маршрут и файлы сохраняются. Это защита текущего владельца Setup и chat-сеанса. Флаг хранится в памяти. Владение уже запущенным runtime по-прежнему имеет отдельную проверку остановки и фактического завершения процесса. ## Приёмка реализации

| Локальная проверка | Наблюдение |
| --- | --- |
| Адреса и формат | TTY/JSONL с буквальными IPv4, одинаковые и публичные адреса, IPv6/порт/CIDR, неназначенный local, off-link, network и broadcast. Использовать существующие тесты префиксов `/23` и `/25`. Отказ оставляет Setup прежним. |
| Сохранение и пути | Fresh Setup сохраняет действительный LAN выбор на уже назначенном Windows интерфейсе. Повтор не пишет, reopen показывает тот же выбор. Явное переключение на loopback сбрасывает только текущий профиль и результаты импорта локаторов. Чужой профиль и reparse target сохраняются. Покрыть drift дайджеста и потерю ответа. |
| Переход без fixture | Два новых Setup от пустого каталога до chat без GUI на одном хосте через loopback. Пока Setup открыт, owner отклонён. После `quit` owner заново проверяет оба импорта, создаёт Profile2 и освобождает state/runtime после завершения. До exchange статус локального IPC доступен без `live_admitted`. После exchange проверить `live_admitted`, сообщение и историю в каждом контексте. |
| Отказы при старте | Недействительное согласие, несовпадающий профиль, второй owner и неподтверждённый cleanup до spawn. Профиль и сообщения сохраняются. Проверка helper cleanup использует существующие focused seams. |

Сетевые Rust harnesses компилировать без запуска и выполнять через стабильный Windows runner. Cargo Idle с одним заданием. Локальная приёмка loopback проверяет переход и двухслотовое общение. В отдельном будущем прогоне физическая пара проходит тот же путь с начала, выбирает зеркальные private IPv4 на реально назначенных интерфейсах и использует согласованные условия входящего UDP и фиксированные пути EXE. Сверить bind, свежие подписанные локаторы, live admission, доставку по обоим слотам и завершение обеих Jobs. Firewall, маршрутизатор и сетевой профиль проектом не меняются.
