### Why129 is insufficient at the required cut

`runtime7/protocol2.rs::prefix2` (434ff) uses `start=next[peer]`, returns no request if that exact pending source exists, computes ordinary credit `64-pending`, and at full64 pending requests **one** head source. After the head is committed, native drain promotes that source plus the64 contiguous pending successors. `verification.rs::page` and `oracle::Pages::accepted` count only non-head pages with actual new sources. Therefore129 outstanding sources can leave only `129-65=64`: four full ordinary16-source pages. Head and zero-new-source replay cannot manufacture page5. Packet-size variation may create more pages, but cannot be assumed. The final plan §6 claim that129 guarantees >=8 is inconsistent with this pending cut.

Only one extra source would guarantee page5, but would not preserve the plan's >=8 premise. Proposed smallest cardinality for that premise: **178=65+113**, so **49 extra sources** beyond129. Preserve exactly129 genuinely offline sources; add49 only after the real64 hold is released and its reservation returns to0, while both C1 live/prefix and ACK paths remain suppressed. Those49 are explicitly online materializations, never described as offline. This is an explicit amendment for root review, not an observed scheduler result or a quiet increase of runtime limits.
