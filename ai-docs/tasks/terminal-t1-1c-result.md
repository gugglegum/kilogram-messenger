# T1.1c. Отмена команд и завершение

База `a68e544236a793dc769426286cde70eacf055469`. Семантика утверждена в [контракте T1.1c](terminal-t1-1c-contract.md).

## Реализация

- Координатор обеспечивает допуск, отмену и завершение независимо от потоков stdin, stdout и последовательного исполнителя. Для correlation ID есть внутреннее поколение. Writer освобождает именно это резервирование перед первым байтом, а continuation истории применяется после ACK. Очередь содержит одну обычную команду. `quit`, `disconnect`, EOF и ошибка потока сразу закрывают допуск и сигнализируют владельцу.
- `OperationControl` защищает границы входа в публикацию, допуска IPC и фиксации единственного ответа. В снимке результата согласованы контекст, request ID, подтверждение DPAPI и receipt. При позднем ответе Recovery сохраняет актуальное состояние, ранее опубликованный результат остаётся прежним. Завершившийся только для клиента вызов удерживает физический слот до окончания работы.
- Stop handle существует до запуска Work. Отдельный cancel действует на команду, а при отмене предварительного owner инициирует его rollback. Observer снимает своё ожидание и закрывается без IPC shutdown. Код 3 сохраняет блокировку нового owner в текущем CLI и означает отсутствие подтверждения stop. Успешная остановка требует выхода и reaping своего процесса, EOF дочерних потоков и удаления собственного descriptor.
- Windows TTY использует уже закреплённый Tokio signal. Обработчик публикует только управляющее событие. Пакетный JSONL-клиент оставляет stdin открытым до нужных ответов: EOF отменяет активную операцию и возвращает `session_closing` для принятой команды, которая осталась в очереди.

## Проверки

- `build06` подтвердил сборку `--locked --offline` с одним заданием Cargo и приоритетом Idle. Постоянный `target/terminal-t1-checks/kilogram-cli.exe` имеет SHA-256 `0156430f997841ffd5c3cb7aab23bb6b27ccf90f5e3e65ab5a4d0c4a06f11854`.
- `parser04` подтвердил девять CLI-тестов. В том числе проверены гонка complete/cancel, занятый слот после консервативного итога, повторное использование ID и слота управляющего ответа до наблюдения предыдущего ACK, а также выходной лимит и continuation R1.
- `fixture03` выполнил три теста. Барьеры проверили отмену до публикации DPAPI, после публикации до readback, после readback до IPC и после принятия запроса runtime с потерянным ответом. Проверена фиксация receipt относительно единственного итога. Перед IPC сохранённый intent был перечитан штатным Store. У первого узла зафиксировано ноль отправок IPC, у второго ровно одна.
- `console03` подтвердил физический Ctrl+C через отдельную ConPTY внутри тестового Job Object. Активную отмену и дальнейшее чтение stdin проверил фиксированный CLI harness с барьером перед операцией. Итоговый продуктовый EXE в своей ConPTY подтвердил явный `/cancel` без активной команды и штатный idle Ctrl+C. Целая консоль или рабочий стол сигналов от драйвера не получали.
- `smoke02` прошёл восемь сценариев на итоговом EXE и свежей DPAPI-паре. После холодного рестарта status/retry восстановили оба прежних ID без дублирования событий или строк у peer. Активный observer отменился, удержал внутренний слот до снятия барьера, допустил последующее использование прежнего correlation ID и вышел при работающем owner. В опыте с EOF настоящий Work удалил descriptor своего runtime до того, как был отпущен удерживаемый исполнитель. Принятая ожидающая отправка получила `session_closing`, а после рестарта runtime вернул `unknown` по этому долговременному ID. Отдельные запуски с забитым и закрытым stdout дали код 2 и убрали принадлежащий CLI descriptor. Весь Job Object по завершении пуст.
- В `fixture04` те же три теста повторены на отдельной свежей паре без остаточных процессов. `startup01` задержал наблюдение выхода реального дочернего процесса тестовым барьером. До подтверждения `Work` удерживал lock Setup, отклонял действия и сохранял исходную причину сбоя. Отмена отдельного старта не изменила сохранённый Setup.
- `ssh01` сверил SHA-256 обоих EXE после передачи в отдельный тестовый каталог на ноутбуке. В закреплённом SSH с `-T` продуктовый CLI подтвердил `target_not_active` и выход по EOF, а фиксированный тестовый harness подтвердил отдельные результаты принятой отмены и активной команды, затем выход по EOF при ещё занятом слоте. Оба процесса завершились с кодом 0. В SSH-сценарии использовались пустые пути Setup, runtime и отправка сообщений на ноутбуке не запускались.
- `gui01` подтвердил три существующих теста общего Recovery, включая реальный GUI worker с `Action::Send` и `RetrySend`, и тест панели GUI. `gui02` повторил тест панели на готовом образе после появления остаточного `vctip` в первом прогоне. Ручной прогон GUI не выполнялся.

У `build06`, `fixture04`, `parser04`, `console03`, `smoke02`, `startup01`, `gui02` и `ssh01` подтверждены child/owner 0, EOF и пустой Job Object без принудительной очистки. Код 3 проверен на управляемом дедлайне координатора. Сценарий удержания блокировки проверен отдельно на реальном дочернем процессе с задержанным наблюдением его выхода.

## Ограничения и сохранённые попытки

Первый запрос на загрузку двух EXE был отклонён auto-review, поскольку разрешение на локальные тесты не подтверждало передачу этому назначению. Файлы не передавались до отдельного явного разрешения пользователя. После него `ssh01` выполнил загрузку и протокольный тест. Нажатие Ctrl+C квалифицировано отдельно в локальной ConPTY.

Первый `smoke01` выявил гонку слота cancel. Клиент уже видел предыдущий ответ, а чтение следующего запроса могло застать слот занятым до обработки ACK. Слот передаётся writer и освобождается перед первой записью. Сценарий повторён на свежей DPAPI-паре. В `console01` дочерний процесс унаследовал перенаправленные stdin/stdout тестового драйвера. Со следующей попытки только тестовый launcher явно задаёт пустые стандартные handles в `STARTUPINFO`, чтобы их поставила ConPTY. `fixture01` остановился на отсутствующем поле в тестовом инициализаторе, который был исправлен.

Исходные неуспешные или неполные квитанции и архивы образов сохранены в `.tmp/terminal-t1-1c`, включая прогоны с кодом дочерней команды 0 и кодом обёртки 1 из-за оставшегося `vctip`. Формат DPAPI, runtime IPC, сетевой протокол и данные пользователя не менялись.
