# T1.1b. Защищённая отправка и восстановление

## Инварианты

- Владелец Setup выполняет отправку последовательно в общем worker. Наблюдатель может читать `request_status` из закреплённого runtime. Send и retry из observer отклоняются до обращения к Recovery, DPAPI и IPC.
- `Store::prepare` использует существующие привязки setup, приглашения, аккаунта, устройства, claim, peer и контекстов. Он синхронизирует ciphertext, публикует с запретом перезаписи и подтверждает содержимое повторным чтением. Только после этого общий Recovery может вызвать `SessionSend::send`. GUI сохраняет прежнюю генерацию ID. TTY показывает свой ID с подтверждённым flush до передачи команды worker. JSONL задаёт ID независимо от корреляции команды.
- `Client2::request_status` читает локальный receipt по паре слот и ID. В ответе есть номер очереди, необязательный event и уровень доставки. Исходного текста в ответе нет. Повторный send с известным ID направляет к статусу. Сохранённые текст и контекст позволяют отдельно отклонить конфликт. Если защищённая запись уже штатно снята, совпадение произвольно поданного текста по одному receipt установить нельзя.
- Retry сначала читает защищённую запись и проверяет runtime status. Подтверждённый receipt сверяется с известным номером очереди и event. При отсутствии receipt отправляются только сохранённые ID и текст, если запись ещё в Prepared и ранее не было подтверждения. Недоступный status означает неопределённость. При пропаже файла, уже подтверждённого текущим Recovery, новый send и повтор блокируются. После холодного старта Accepted продолжает защищать от потери ранее подтверждённого запроса, пока сама запись на месте.
- Состояния защиты, локальной очереди, появления в истории и подтверждения доставки различаются. Проверка допуска сохраняет условия GUI, включая возможность локальной очереди при недоступном peer. Форматы DPAPI, протокола и хранилища остаются прежними.

## Сценарии проверки

- Прямой DPAPI round-trip и повтор после потери результата до IPC и после принятия runtime. Для каждого случая проверить тот же ID после рестарта, в том числе возможность или запрет повторного IPC.
- Проверить оба направления и контекста на локальной паре, очередь при отключённом peer, историю после переподключения, отказ observer, конфликт текста и неверный контекст. Проверить одну запись у peer для каждого восстановленного запроса.
- Повторить выбранные тесты GUI-пути, детерминированные проверки Recovery и ограничения вывода R1. Ctrl+C и `cancel` остаются отдельными критериями полной T1.1.

## Интерфейс

TTY принимает обычную строку, `//` для экранирования начальной косой черты и `/send <текст>`. Перед передачей send владельцу TTY показывает ID и подтверждает запись в stdout. `/status <request_id>` и `/retry <request_id>` работают в выбранном диалоге.

JSONL принимает `send(context,request_id,text)`, `request_status(context,request_id)` и `retry(context,request_id)`. У результата валидной команды отдельные поля `id`, `context` и `request_id`. `value.state` различает `unknown`, `unconfirmed`, `retry_available`, `queued`, `materialized` и `delivered`. `value.protected` сообщает о подтверждённой локальной записи и об её подтверждённой очистке при согласовании. `null` означает, что результат не подтверждает состояние этой записи. `value.event_id` появляется по подтверждению из runtime. Повторная подача текста с известным ID возвращает `request_known` или конкретный конфликт, если он доказуем по защищённой записи. Запрос статуса не принимает текст.

## Результаты

- `build03` подтвердил сборку CLI с `--locked --offline`, Cargo Idle и одним заданием. Постоянный EXE `target/terminal-t1-checks/kilogram-cli.exe` имеет SHA-256 `5faf4a94f4e10c74bacdd9a9f66577c0d3b205937691954cc910cff5697aa404`.
- `fixture02` на свежей локальной DPAPI-паре прошёл оба целевых теста. Тестовый адаптер перечитал запись штатным Store и прервал первую попытку до IPC, а у второго запроса отбросил ответ после принятия runtime. Зафиксированы соответственно ноль и одна попытка IPC send. Второй тест подтвердил блокировку при исчезновении или подмене уже прочитанной записи. Сохранены исходные квитанции `build01`, `build02` и `fixture01`. В них дочерняя команда завершилась с кодом 0, а обёртка вернула 1 после завершения остаточного `vctip`.
- `smoke02` использовал тот же CLI после холодного старта обоих владельцев. Запрос без предшествующей отправки прошёл `retry_available → queued → materialized → delivered`. У ранее принятого запроса status и retry вернули исходный event. Для каждого из двух запросов обе истории содержали по одной записи с тем же event и исходным текстом. Проверены неизвестный ID, конфликты текста и контекста, JSONL-отправка в обоих направлениях и контекстах, отказы наблюдателя и TTY-команды. На обеих копиях удалены штатно закрытые IPC descriptors и согласованные pending intents. `build03`, `fixture02` и `smoke02` завершились с кодами child/owner 0, EOF и пустым Job Object без принудительной очистки.
- `smoke01` сохранён как неуспешный прогон. Первый драйвер дошёл до восстановления записей, но не дождался доставки после холодного рестарта. В `smoke02` свежие loopback-локаторы обменивались через диагностические CLI-команды. Терминальные команды обмена локаторами не добавлялись.
- `parser02` подтвердил семь CLI-тестов, в том числе независимые ID отправки и корреляции, точные границы вывода R1 и повтор истории с тем же курсором. `gui01` подтвердил три ранее существовавших теста общего Recovery, включая реальный сценарий GUI worker с `Action::Send` и `RetrySend` после рестарта, и один тест панели GUI. У `parser01` и `gui01` код дочерней команды 0, код обёртки 1 из-за остаточного `vctip`. Повторы `parser02` и `gui02` на готовых образах дали child/owner 0, EOF и пустой Job Object без принудительной очистки. `gui02` повторил тест панели. Визуальный интерфейс GUI вручную не прогонялся.

Артефакты находятся в `.tmp/terminal-t1-1b`. Проверенные T1.1a CLI и GUI образы сохранены в архиве, а стабильный путь старого тестового EXE `kilogram-first-dialog` был перезаписан при первой сборке T1.1b. Для старого образа сохранены хеш и исходные логи. `cancel` и Ctrl+C ещё требуются для полной T1.1. Проверка отправки по SSH и полевой сети в этот прогон не входила.
