# CS3.3a — защищённая отправка и типизированный IPC

Baseline `0ee7058539a2fd75fac91e0001c8b66687461bf8`. Срез готовит защищённую отправку, восстановление запроса и чтение истории для следующего этапа интерфейса. [Контракт](E:/AI-Projects/kilogram-p2p-messenger/ai-docs/tasks/clean-start-cs3-3-send-history-contract.md) · [Поправки ревью](E:/AI-Projects/kilogram-p2p-messenger/ai-docs/tasks/clean-start-cs3-3-contract-review-01.md)

- `Client2` добавляет op 2/3/4 на существующем подписанном descriptor. Проверяются ожидаемый context, точные поля ответа, связь между event и delivery, количество и размеры строк, canonical cursor и прежние view/frontiers. History запрашивает до 32 строк. Сервер сокращает страницу по byte cap, а переход управляется `finished`. Текст, cursor и raw errors отсутствуют в Debug новых DTO и ошибок. Существующая обработка CLI, status, locator и Shutdown сохраняется.
- Desktop пишет один DPAPI CurrentUser intent на Setup. До первого op 2 ciphertext проходит sync, публикацию без перезаписи и повторное чтение. Точные UTF-8 байты и request16 защищены вместе с привязкой Setup, приглашения, обоих участников, claim, упорядоченных contexts и выбранного слота. Неизвестная или испорченная запись блокирует отправку. Только распознанный staging остаток может быть убран после проверки конечного пути.
- `Prepared` восстанавливается через op 3. Явный повтор требует свежего Absent и использует те же ID и байты. Положительный lookup не вызывает op 2. После принятия сравнивается queue sequence, после подтверждённой материализации удаляется защищённый intent. Если запись Accepted не удалась, текущий worker помнит подтверждение и не превращает последующий Absent в возможность повтора. Подтверждённые конфликты сохраняют запись и блокируют отправку.
- Действия send/retry входят во внутреннюю очередь прежнего owned worker. Worker также уточняет уже существующую запись после запуска и добавляет безопасный статус без текста сообщения. Проверка PID/instance и descriptor, одно выполнение за раз, generation, cancel и остановка с удержанием Setup до exit сохраняются. Для записи в очередь требуется свежий подходящий статус выбранного слота и валидное согласие. Lease собеседника для локальной очереди не требуется.

DPAPI защищает файл от чтения без доступа к ключам текущего пользователя. Процессы того же пользователя, rollback обоих хранилищ и внезапная потеря питания выходят за пределы гарантий. Сохранённый intent занимает одно место для обоих слотов до материализации и очистки. Включение composer, отображение страниц и двухоконная GUI-проверка относятся к CS3.3b после приёмки и публикации этого среза.

## Проверка

- **Реальные runtime и IPC.** Свежая пара с независимыми Root, подписанный обмен локаторами и оба текущих Active2. Тест перехватил успешный op 2 после фактического приёма, не передав ответ машине состояний. До отправки проверен существующий защищённый intent. После штатного выхода runtime локальный store показал те же ID, точные байты, event и durable receipt. Reopen Setup и runtime вернул положительный op 3, без op 2 со стороны восстановления. Отдельный диагностический повтор исходных байтов сохранил очередь и event. Иные байты получили `RequestIdConflict`.
- **История через реальные кадры.** Запрос limit32 вернул смешанные страницы из коротких строк и двух текстов по 4096 максимально экранируемых байт. Первая короткая страница не была концом. На обоих узлах прошли по двум страницам без пропуска, повторения и изменения event или байтов. Продолжение прежнего cursor исключило дописанную строку, новый snapshot включил её. Проверены повтор страницы, изоляция второго слота и отклонение чужого context cursor.
- **Owned worker с отключённым peer.** Подготовленный файл существовал до dispatch. При открытии worker подтвердил Absent и ожидал явного Retry. Retry использовал исходный ID и текст, отдельный Send сохранился после очистки. Холодная история подтвердила ровно две записи во втором слоте и отсутствие подтверждения доставки при отключённом peer. Все product runtime этой проверки закрылись штатно.
- **Контролируемые сбои и DPAPI.** Actual CurrentUser round-trip и Windows reparse refusal. Проверены девять несовпадающих bindings, повреждённый и слишком большой blob, staging после прерывания, неизвестный файл, максимальный escaped текст, запрет второй pending записи. Инъекции ошибки публикации, смены фазы и удаления проверяют границы без отказа реального диска. После Known Accepted ответ Absent сохраняет Conflict. Синтетические маркеры искались в ciphertext, обычном Setup, доступном runtime выводе и receipts без печати текста. Отдельный Windows пользователь не проверялся.
- **Codec.** Проверены виды/версии/opcodes, формы опций и delivery/event, cursor/progress/размер/число строк и безопасные ошибки. Клиент не переносит произвольный runtime error в UI.
