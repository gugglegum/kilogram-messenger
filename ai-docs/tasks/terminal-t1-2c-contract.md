# T1.2c. Взаимное согласие на два контекста в терминале

База `52200d9169a1c543a3047aac41b4c3baca48652a`. Оба владельца открыли свои Setup, сохранили слова восстановления и подтвердили личности друг друга через T1.2b. Они обмениваются публичными документами proposal и final, затем каждый устанавливает согласие в своей локальной базе. Проверка импорта действует для двух фиксированных контекстов в исходном порядке. Настройка LAN, запуск runtime и переход в chat относятся к следующему срезу. [Приглашение и ответ](terminal-t1-2b-contract.md) · [Границы T1](terminal-t1-contract.md)

## Роли и команды

`consent::role` вычисляет роль по порядку байтов `device_id`. Меньший ID у `proposer` (роль 0), больший у `cosigner` (роль 1). Сравнение выполняется после проверки готовности аккаунта, сохранения слов и наличия отдельного peer. `peer_selection.role` по-прежнему показывает роль в обмене приглашением. Любой из участников этого обмена может оказаться proposer. [Вычисление роли](../../crates/kilogram-first-dialog/src/consent.rs#L240) · [Действующий экран Windows](../../apps/kilogram-windows/src/fresh_onboarding/mod.rs#L707)

| TTY | JSONL `op` и `args` | Успешный `value` |
| --- | --- | --- |
| `/consent propose` | `consent_propose {}` | Снимок Setup. Роль 0 создаёт или доводит до конца оба подписанных предложения. |
| `/consent export` | `consent_export {}` | Публичные метаданные `A` и `path`. Роль 0 получает `exchange/proposal.kilogram`, роль 1 получает `exchange/final.kilogram`. |
| `/consent inspect <proposal\|final> <путь>` | `consent_inspect {"kind":"proposal\|final","path":"<путь>"}` | `A` и `preview_id` после проверки обоих слотов. Proposal принимает на просмотр роль 1, final принимает роль 0. |
| `/consent accept <proposal\|final> <preview_id>` | `consent_accept {"kind":"proposal\|final","preview_id":"<id>","confirmed":true}` | Снимок Setup после сохранения просмотренного предложения или final. |
| `/consent cosign` | `consent_cosign {}` | Снимок Setup. Роль 1 подписывает оба контекста принятого предложения и сохраняет свой final. |
| `/consent import` | `consent_import {}` | Снимок Setup после успешной установки или повторной проверки обоих локальных контекстов. Роль 0 использует принятый final, роль 1 использует свой сохранённый final. |

Команды сохраняют ответ JSONL v1 `{"v":1,"type":"result","id":"<request_id>","ok":true,"value":…}` либо `{"v":1,"type":"result","id":"<request_id>","ok":false,"code":"<code>"}`. Формат `A` содержит `kind`, `invitation_id`, `contexts` из двух ID, `sender` и `recipient` в форме `{account_id,device_id}`, `not_before`, `expires_at` в секундах Unix и `artifact_digest` (BLAKE3 канонической сериализации проверенного `Envelope`). Метаданные экспорта соответствуют байтам, записанным или уже лежащим по возвращённому пути. TTY показывает полные ID, порядок контекстов, срок действия, дайджест и ID просмотра. `accept` в TTY и буквальное `confirmed:true` в JSONL означают подтверждение именно этих данных. `propose` и `cosign` отдельно разрешают подпись, `import` отдельно разрешает локальную установку. ## Просмотр, подтверждение и сохранение

- **Чтение и проверка.** Прочитать файл один раз в пределах `artifact::FILE_CAP` и декодировать `Envelope`. Из `consent::select` выделить общую проверку без записи, которую вызывают inspect и select. Сопоставить тип, направление, полную `Identity` отправителя, recipient, invitation и оба упорядоченных контекста с Setup. Для proposal проверить обе подписи proposer, привязки каждого слота и общий период. Для final проверить membership, подписи согласия обоих устройств, Fresh и период, затем `lineage` относительно точных сохранённых proposal слотов. Проверить уже зафиксированные inputs и занятые целевые имена, включая оставшиеся файлы без reference после прерванной записи. Различающиеся байты или привязки отклонить до записи. Подписи относятся к проверенным payload; внешние поля JSON-конверта сверяются с сохранёнными локальными привязками.
- **Подтверждение.** Общий слот T1.2b хранит типизированный pairing или consent preview. Consent preview держит неизменяемый декодированный `Envelope`, его тип и ID. Команда с верным ID и типом погашает preview, обновляет проверку Setup под тем же lock и повторяет проверку привязок, конфликта и срока перед записью. Путь из inspect больше не используется. Новый запущенный inspect любого типа, `begin/open`, `/preview clear` и завершение процесса очищают слот. Ошибка разбора, `busy` до dispatch и неподходящий ID/тип не погашают текущий preview. Команда подтверждения выполняется только после успешного ACK записи результата inspect; при сбое вывода сессия закрывается. После потери ответа на accept сначала проверить `open/status`: сохранённая ссылка остаётся действительной. Повтор accept требует нового inspect и нового подтверждения. Тот же документ сохраняет ту же ссылку; конфликтующий документ не заменяет её.
- **Локальные файлы.** Сохранение и экспорт опираются на существующие frozen inputs, `Reference` и no-clobber. До записей под `consent` и `exchange` применить существующую проверку путей под Setup без reparse и перехода в приватное хранилище. Повтор export возвращает тот же файл при совпадении байтов; выход с чужими байтами сохраняется. Роль 1 устанавливает свой final прямо из сохранённой ссылки. Передавать между Setup нужно только публичные `proposal.kilogram` и `final.kilogram`.

## Снимок состояния и повторы

Сохранить текущий формат Setup и добавить `consent` к публичному снимку готового Setup с подтверждённым peer. Внутри `role` равна `proposer|cosigner`, `stage` принимает `not_started`, `in_progress`, `proposal_ready` (роль 0 сохранила оба proposal-выхода), `proposal_selected` (роль 1 приняла proposal) или `final_saved` (есть ссылка на final). Приоритет у самой дальней стадии. `not_before` и `expires_at` равны `null` до freeze, затем содержат неизменяемый интервал. `validity` равна `unset|current|not_current`. `selected_proposal_digest` и `final_digest` содержат публичные дайджесты из сохранённых references или `null`. `slots` содержит два элемента `{context_id,signing,importing}` в порядке Setup. Оба outcome используют `not_started|started|accepted|failed`. При `started` результат неизвестен. При `failed` успех helper не подтверждён и возможен повтор точного ввода. `signing:accepted` отражает собственную подпись устройства. Поле `local_installation` показывает результат локальной установки.

- `unconfirmed` до успешной проверки обоих слотов, включая частичный результат.
- `previously_accepted`, если в записи оба импорта `accepted` и в текущем снимке нет действующего подтверждения.
- `confirmed_current_session`, если `execute(Import)` завершился успешно для обоих слотов и период действителен сейчас.

Снимок отражает последние завершённые операции. `status` во время действия читает предыдущий снимок без параллельной проверки файлов. Writer пересчитывает `validity` через `valid_interval` непосредственно при сериализации status и результата с Setup, после ожидания очереди. При недействительном периоде он показывает `previously_accepted` вместо отметки текущего подтверждения, сохраняя оба durable outcome. При новом открытии Setup проверяются ссылки и подписи через `review(false)`, включая просроченные сохранённые документы. После reopen оба `accepted` означают `previously_accepted`. Текущую действительность проверяют перед действиями через `review(true)` и `valid_interval`. Истёкшие или ещё недействительные данные сохраняют прежние outcome. Повтор сохраняет тот же период. Локальная установка подтверждает только импорт на этом устройстве. Итоги импорта у peer и подключения требуют отдельных проверок.

`execute` валидирует оба final до первого импорта. Если операция прервалась, сохраняются exact finals и все записанные outcomes. Повтор `import` снова проверяет и предъявляет **оба** exact слота существующему `ordered context2-import`. Уже установленный слот подтверждается идемпотентно, отсутствующий устанавливается. Это относится и к `started` после коммита helper без записи результата, и к потере терминального ответа после записи `accepted`. Повтор подписи сохраняет принятые выходы и использует новое имя попытки для неподтверждённого слота, сохраняя предыдущую попытку. ## Выполнение и ошибки

Один действующий Setup lock, worker и writer с generation ACK. `propose/cosign/import` выполняют существующий `consent::execute` с путём к текущему `kilogram-cli.exe`, полученным при старте через `current_exe`. Соседний `kilogram-bootstrap.exe` по-прежнему обслуживает создание аккаунта; команды `ordered` принадлежат CLI. Расширить действующий маркер отмены активной операции на эти три команды. Пробросить тот же токен в оба последовательных helper и использовать существующие предел 60 с на дочерний процесс и ожидание завершения после остановки до 5 с. `cancel`, Ctrl+C и закрытие используют действующую привязку к generation. Согласовать завершение и отмену до публикации результата: при выигравшей отмене не выдавать новое подтверждение установки, сохранить фактически записанные outcomes. Подтверждённые записи остаются после потери вывода. `cleanup_unconfirmed` завершает сессию по действующему пути ошибки. | Точка отказа | Код |
| --- | --- |
| Нет открытого/готового Setup, подтверждения слов или peer, Setup lock занят | `not_open`, `invalid_state`, `recovery_required`, `peer_required`, `setup_locked`. Повреждение Setup или сохранённых references при open/refresh даёт `setup_invalid`. |
| Нечитаемый вход, неверная структура или подпись, другой тип, pins или lineage | `artifact_unreadable`, `artifact_invalid`, `wrong_artifact_kind`, `consent_mismatch`. |
| Неверная роль, отсутствует принятый proposal/полный final или незавершён export, недействительный срок | `wrong_consent_role`, `consent_not_ready`, `consent_not_current`. |
| Разные frozen inputs или занятое место для выбранного документа, конфликт экспорта, другой сбой записи | `consent_conflict`, `export_conflict`, `consent_failed` либо `export_failed` для экспорта. |
| Нет пригодного preview, нет явного подтверждения, очередь занята | `preview_required`, `invalid_args`, `busy`. |
| Helper не запустился, превышен срок, действие отменено, завершение процесса не подтверждено | `helper_unavailable`, `helper_timeout`, `cancelled`, `cleanup_unconfirmed`. Обычный неуспех подписи даёт `consent_sign_failed`, обычный неуспех импорта даёт `consent_import_failed`. |

Коды получают из типизированных точек отказа. `HelperError` сохраняет причину даже при неудачной записи `Failed`. `CleanupUnconfirmed` имеет приоритет и закрывает сессию через существующий bounded shutdown. Отмена, зафиксированная до завершения операции, сбрасывает `consent_confirmed` даже после обоих записанных `accepted`. Точный повтор import может восстановить подтверждение. Обычный отказ `context2-import` включает возможный lock базы или проверку владельца. Имеющегося статуса процесса для различения этих причин недостаточно. TTY сообщает, что следует закрыть удерживающий базу runtime, если он запущен, и повторить с теми же finals. Текст ошибок helper, argv, ключи и слова в вывод не передаются.

## Локальная приёмка реализации

| Сценарий | Проверка |
| --- | --- |
| Два свежих терминальных Setup без fixture | Полный обмен от invite/reply до обоих локальных import. Получить оба случая через ограниченное число новых пар с реальными ID: inviter в роли 0 и inviter в роли 1. Проверить TTY и JSONL, оба контекста/полные pins и фактическую установку в каждой базе. |
| Отказ и подмена | Входы с чужим sender/recipient или контекстом, переставленными слотами, неверной lineage и истёкшим сроком. После отказа сравнить setup.json, references, файлы и состояние базы. Между inspect и accept заменить входной файл; подтвердиться может только показанный дайджест. Проверить clear, неправильный ID/тип, `confirmed:false`, отказ writer и повтор после погашения preview. |
| Реальная частичная установка | На тестовой копии занять `consent/import-1.context` другими байтами. Проверить фактический импорт слота 0, отказ слота 1, сохранность конфликтующего файла и отсутствие общей отметки установки. Сохранить тестовый конфликт отдельно, затем повторить exact final: слот 0 не создаёт новый коммит, ставится только слот 1. Для коммита без получения результата использовать имеющийся `execute_with(..., after)` в тесте согласия. |
| Повтор и новый процесс | После потерянного ответа и при явном повторе export возвращает те же байты, import не меняет поколение уже установленной базы. Новый процесс открывает тот же Setup, показывает тот же период, references и outcomes (включая `started` при потере результата). Только новый успешный import даёт `confirmed_current_session`. Проверить открытие просроченных данных и запрет действий с ними. |
| Закрытие и отмена | Во время операции status остаётся доступен. Cancel по текущему ID и quit/EOF перед остановкой helper сохраняют запись и закрывают Setup lock после завершения процесса. Просроченный ACK или ошибка writer не выпускают второе действие. |
| Граница времени | Сериализовать один кешированный снимок на `expires_at - 1` и точно на `expires_at`, без ожидания системных часов. Подтверждение текущего сеанса пропадает на границе, durable accepted остаётся. |

Достаточны целевые локальные Windows проверки через стабильные имена harness и CLI. Для сборки использовать пониженный приоритет. [Действующий тест частичных результатов и reopen](../../crates/kilogram-first-dialog/src/consent_tests.rs#L187) · [Правила Windows](../../AGENTS.md)
