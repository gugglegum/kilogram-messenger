# T1.1e1. Инкрементальное чтение истории для терминала

Проект для архитектурной проверки на базе `ab3e02fe756b636a8a168211f1cc27fe4e89010a`. Срез добавляет две операции чтения к локальному IPC Fresh runtime2 и проводит их через общий `Chat`. Они фиксируют границы хвоста и используют действующую пагинацию для чтения новых строк. Сетевой протокол, данные хранилища, формат и MAC курсора, семантика `history_page` и DPAPI сохраняются. Планировщик и вывод уведомлений вынесены в [T1.1e2](terminal-t1-1e-contract.md).

## Операции

Обозначения по ролям 0 и 1. `F` — исключающие верхние границы предыдущего среза, `G` — границы текущего среза, `next` — следующий ordinal каждой роли. Ordinal 0 принадлежит genesis. Пагинация текстовых строк начинается с 1.

| Операция | Результат |
| --- | --- |
| `history_anchor(slot, context)` | Сервер читает и проверяет метаданные view и текущие Heads. Запечатывает позицию с `frontiers = next = G`. Возвращает завершённую позицию на текущем хвосте. |
| `history_follow(slot, context, completed_cursor)` | Сервер аутентифицирует курсор, проверяет `1 <= next = F <= G` по обеим ролям, запечатывает `frontiers = G, next = F`. Возвращает начальную позицию фиксированного диапазона. При `F = G` она уже завершена. |
| Существующая `history_page(slot, context, cursor, limit)` | Читает от полученной позиции до `G` тем же причинным слиянием, возвращает непрозрачный курсор продолжения или завершения. Запрос без курсора продолжает открывать обычный snapshot с `next = [1, 1]`. |

Открытие диапазона и чтение его первой страницы — два коротких запроса. Полученный start cursor позволяет повторить **также первую страницу** при том же limit после конкурентного append, с теми же строками и следующим cursor. Все страницы используют одно `G`. Повтор `follow(F)` без полученного start cursor заново фиксирует текущие Heads и может выбрать больший `G`. Сбор уведомлений начинается после получения start cursor, поэтому потеря первого ответа не пропускает строки. Завершённый курсор обычной истории, anchor или дочитанного delta допустим на входе follow. Старый завершённый курсор той же валидной области годится для повторного чтения. На клиенте повтор уже обработанного checkpoint ограничивает поколение и текущая позиция.

## Почему диапазон можно открыть по старым границам

- **Атомарный срез.** `history_view` читает аутентифицированные Identity и Heads относительно одного root внутри `begin_read`. Она проверяет инкарнацию, context, view и количество записей обеих Lane. В Fresh runtime2 append и чтения идут через последовательные задания одному `Owner2`. Внутри одной read transaction у новых операций используются те же `Work`, Identity и Heads для аутентификации входа, проверки границ и выдачи курсора. Новый append виден операции целиком или остаётся за её границей. Следующая страница открывает свою read transaction и проверяет сохранённую границу курсора относительно новых Heads. [Чтение root](../../crates/kilogram-state/src/vault/indexed_dialog/history.rs#L223) · [Проверка Identity/Heads](../../crates/kilogram-state/src/vault/indexed_dialog/history.rs#L415) · [Owner2](../../apps/kilogram-cli/src/ordered_dialog/runtime2/runtime.rs#L30)
- **Префикс причинно замкнут.** Init ставит `[1,1]`. Пишущий путь Protocol2 проводит text batch через `history_rows`. Новая строка должна занять ровно текущий ordinal своей роли и указывать на её текущий tail. Любой явный родитель должен соответствовать Event/Lane, указанной роли и ordinal строго ниже **текущей** границы его роли. Родитель из той же пачки возможен только среди уже принятых строк в `staged`. Строка, Lane и продвинутые Heads входят в один план записи. По индукции каждый сохранённый срез `F` содержит всех родителей своих строк и остаётся тем же набором событий после более позднего append. Индекс разрешает прежнему Event/Lane только тождественную повторную запись. [Путь Protocol2](../../crates/kilogram-state/src/vault/indexed_dialog/history_protocol2.rs#L1048) · [Проверки append](../../crates/kilogram-state/src/vault/indexed_dialog/history_writer.rs#L584) · [Продвижение Heads](../../crates/kilogram-state/src/vault/indexed_dialog/history_writer.rs#L740) · [Неизменяемые ключи](../../crates/kilogram-state/src/vault/indexed_dialog.rs#L1547)
- **Обе роли.** При старте с `next = F` условие `parent.ordinal < next[parent.role]` уже выполнено для всех родителей из старого среза. Родитель в delta становится доступен после чтения его Lane в текущем проходе. Слияние выбирает минимальный ID среди готовых кандидатов, проверяет источники и не требует, чтобы `F[0] = F[1]`. Выдаваемый порядок — причинный порядок внутри диапазона. Простая фильтрация нового полного snapshot по позиции в общем порядке могла бы выбрать другой хвост. [Слияние](../../crates/kilogram-state/src/vault/indexed_dialog/history.rs#L83) · [Проверка кандидата и родителей](../../crates/kilogram-state/src/vault/indexed_dialog/history.rs#L470)
- **Подлинность позиции.** Существующий MAC связывает обе пары ordinal с инкарнацией, view, контекстом, диалогом, epoch диалога и SID. Сервер проверяет `next = frontiers` сам. Курсор выдаёт только сервер. Клиент хранит его как непрозрачное значение. В рамках непрерывного владельца действуют описанные инварианты append. После восстановления старого образа хранилища новое подключение считается новым поколением наблюдения. У курсора нет срока действия или гарантии обнаружения восстановления образа с тем же view, если его Heads успели снова достигнуть прежних границ. [Seal/authenticate](../../crates/kilogram-state/src/vault/indexed_dialog/history_cursor.rs#L73)

## Локальный API, отказы и границы

Запросы nested IPC — CBOR-массивы `[2, 16, slot]` и `[2, 17, slot, cursor: bstr275]`. Успешный ответ — `[2, opcode, [context: bstr32, view: bstr32, [F0, F1], [next0, next1], cursor: bstr275]]`. `F` в ответе означает его верхние границы, то есть `G` в операции follow. `finished` выводится из равенства двух пар. Максимум canonical CBOR равен `3 + 1 + 2*(2+32) + 2*(1+2*9) + (3+275) = 388` байт. С внешним ответом Postcard `OrderedDialog` и его префиксом TCP это `388 + 1 + 2 + 4 = 395` байт при бюджете 512. Используются существующие descriptor, аутентификация и границы transport frame. [Dispatch](../../apps/kilogram-cli/src/ordered_dialog/runtime2/runtime.rs#L1403) · [Фрейм Client2](../../crates/kilogram-runtime-ipc/src/ordered2.rs#L184) · [Внешняя рамка](../../crates/kilogram-runtime-ipc/src/lib.rs#L2342)

- Типизированный `Client2` предварительно сверяет context/slot, затем проверяет версию, opcode, форму, размер и диапазоны. Сервер аутентифицирует входной MAC до доверия ordinal. Для ответа клиент сопоставляет context/view/frontiers/next с полями фиксированного формата возвращённого курсора. Он хранит токен целиком, без поля для записи ordinal и без собственного MAC. На follow клиент проверяет тот же view, `next` точно равное прежним завершённым frontiers и обе новые границы не ниже. Старый runtime, сообщивший `UnsupportedOperation`, даёт `HistoryPositionUnsupported`. Обычная история продолжает работать, tail-клиент не подменяет отказ сканированием. [Типизированные ответы](../../crates/kilogram-runtime-ipc/src/ordered2/messaging.rs)
- Владелец проводит операции через действующие `Chat`, `Work` и `Session` с теми же scope/descriptor/child checks до и после IPC. Observer использует существующие проверки descriptor, runtime instance и обоих context. Для e2 общий сервис даёт проверенную собственную роль каждого слота из `DialogScope` владельца или проверенного `Status2::installed` наблюдателя. `OperationControl` и `SessionStop` ограничивают ожидание. Уже допущенная read-only работа в Owner2 может закончиться после отмены ожидания. Принять её ответ можно только для действующего поколения запроса. [Владелец](../../crates/kilogram-first-dialog/src/connection.rs#L910) · [Observer](../../crates/kilogram-first-dialog/src/chat.rs#L462) · [Отменяемое IPC](../../crates/kilogram-first-dialog/src/operation.rs#L193)
- При отсутствии обеих записей Identity/Heads вернуть `HistoryUnavailable`. Инициализированная пустая история даёт завершённый anchor `[1,1]`. Одна отсутствующая запись, некогерентные границы или повреждение дают ошибку. Подмена MAC, чужой контекст/хранилище/view или незавершённый курсор дают `InvalidCursor`. Регресс хотя бы одной границы при той же Identity даёт `SnapshotUnavailable`. Эти ошибки до выдачи новой позиции. Клиент отображает их типизированно без передачи диагностических деталей. Ввод за пределами `1..=32` отклоняется в обычном page. Anchor/follow лишь сравнивают `u64` покомпонентно. Для продвижения страницы и append остаётся `checked_add`. Завершённая граница `u64::MAX` допустима, перевод через неё невозможен.
- Anchor и follow, в том числе idle probe, выполняют до трёх индексных `hget` для Identity, Heads и проверки статической привязки Protocol2. Они не загружают кандидатов или тексты. Страница delta использует индексные lookup от `next`. Для предыдущей Lane и явных родителей остаются точечные проверки, включая чтение старой проекции или источника родителя, если в delta на него есть ссылка. Старые строки не перебираются и не выдаются. Число загрузок кандидатов на страницу не больше `items.len() + 2`. Обращения к узлам индекса зависят от его глубины. Все операции открывают только read transaction. У выдаваемой страницы остаются 32 строки, JSON **48 КиБ минус 512 байт** и общая рамка IPC **48 КиБ**. Курсор продвигается только за вошедшие строки после успешного кодирования. [Статическая привязка](../../crates/kilogram-state/src/vault/indexed_dialog/history_protocol2.rs#L536) · [Пределы чтения](../../crates/kilogram-state/src/vault/indexed_dialog/history.rs#L279) · [RuntimeRepository](../../crates/kilogram-state/src/vault/indexed_dialog/runtime2_read.rs#L305)

## Проверки для приёмки реализации

| Проверка | Наблюдение |
| --- | --- |
| Причинный диапазон и границы | В двух контекстах взять разные `F` по ролям, в одном контексте первый рост только одной роли. Добавить родителей из префикса и из delta в обоих направлениях. Читать страницы с limit 1, добавить строки после открытия диапазона и между страницами. Повтор первой и следующих страниц с тем же входным курсором и limit возвращает те же ID, порядок и cursor. После завершения следующий follow отдаёт поздний append без повторов. Сверить строки с явной историей и отношения parent-before-child. |
| Scope и пустая история | Проверить uninitialized, пустую и непустую историю, чужой слот или scope, подмену токена, незавершённый токен в follow и регресс одной роли. Проверить новую инкарнацию/view и допустимый повтор завершённого токена после штатного reopen того же хранилища. Пределы ordinal проверить малым тестом выбора позиции с синтетическими границами, без генерации больших ordinal на диске. |
| Стоимость и отсутствие записей | На двух подготовленных историях, например 32 и 512 строк, сравнить anchor, idle follow и одинаковый хвост из трёх строк. Использовать существующую синтетическую fixture, `HistoryReadStats` и тестовый учёт ordinal загруженных кандидатов. Для anchor/idle требуются ≤3 point gets, 0 кандидатов и 0 выданных байт текста. Для delta кандидаты только из `[F,G)`, максимум две живые записи, `point_gets <= 40 * (limit + 2) + 3` для Protocol2. Записать nodes_read и values_read, учитывать глубину дерева. В изолированном сценарии без append сравнить root bytes, generation и записи до/после. Тяжёлый benchmark 100000 строк в этот гейт не входит. |
| Caps и пути IPC | Max UTF-8 и экранируемый текст должны уменьшать страницу по размеру без пропусков и пустой незавершённой страницы. Проверить malformed position reply, неверный slot/opcode, старый runtime, owner/observer, остановку ожидания, прежние snapshot-регрессии и отсутствие побочных эффектов у новых вызовов. Интеграция Fresh runtime2 проходит через стабильный Windows harness на тестовых копиях. |
