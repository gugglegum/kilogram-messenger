## Наблюдаемый результат

Два materialized сообщения A, по одному в каждом установленном контексте, переживают **штатный** перезапуск A при всё ещё выключенном B. До запуска B новый runtime A возвращает прежние `(context, request_id, event_id)` и точные сохранённые строки, оба запроса остаются materialized/not-delivered. После возвращения B они доставляются автоматически; B отвечает один раз в каждом контексте. Итог: четыре уникальных события, одинаковые истории2строки/контекст/хост, явный notification verdict и полная очистка всех инкарнаций. Оба клиента используют прежние Setup/profile/account/device/context identities; без повторного onboarding/consent/manual locator exchange.

## Предпосылки, проверенные по исходникам

- **Долговечность и lookup.** `runtime2/runtime.rs:1293` открывает прежний `RuntimeRepository` под directory lock и проверяет device/context pins; `owner.rs:253` восстанавливает установленные phase3 snapshots/frontiers. `kilogram-state/.../history.rs:567` читает request из сохранённого history view; `runtime2_read.rs:115–145` определяет queued/materialized/delivered через request/event и согласованность persistent receipt/Undelivered. IPC opcode3 (`runtime.rs:1654`) читает именно repository, а не память прошлого frontend. Внешний `request_status` возвращает state/event_id; queue_sequence остаётся внутренним полем и не требуется от отсутствующего JSON API.
- **Нет peer-зависимости локального доказательства.** `connection.rs:1336` делает lookup через закреплённый IPC-клиент без live-peer authorization; history устроена аналогично. `chat.rs:377–398` требует работающий local scope, не `live_admitted`; `connection.rs:1038–1049` разделяет local phase3 send-slots и live connectivity. Поэтому после A-restart допустим owner/phase3/local-ready при `live_admitted=false`. Проверка без B — source-backed ожидание, ещё не новый runtime-result.
- **Автоматическая отправка.** `data.rs:298/334` сохраняет очередь/материализацию через Local commit. `network.rs:96–120` берёт delivery window из persistent debt, после свежей peer authorization; `runtime.rs:610/1195` повторяет delivery rounds с cursor1, а responder-путь `runtime.rs:825/897` также вызывает live window. Сохранённый materialized outbox не нуждается в повторной регистрации через frontend. `send_recovery.rs:469–520` удаляет protected intent после materialized/delivered; это не удаляет runtime request/debt. `send_recovery.rs:283–346` допускает Status lookup прежнего ID при отсутствии intent. В новом сценарии **никаких send/retry для старых запросов**: unknown/смена ID/неавтоматическая доставка — FAIL с диагнозом, а не скрытое восстановление retry.
- **Consent и notification.** Fresh Propose фиксирует30дней (`consent.rs:24/807`), обе стороны продолжают проверять абсолютный interval и policy; продления/смены часов нет. `monitor.rs:104/290/406` создаёт свежий anchor, не persistent cursor между Chat-процессами. Сохраняем принятую границу: queued event, отсутствующий в первом post-watching snapshot B, требует notification; уже присутствующий без notification даёт unproven coverage, не ложный delivery fail или notification success. Все наблюдённые events уникальны и точно связаны; два online reply events обязательны на новом A после подтверждённого watching. Финальная сверка учитывает все старые/новые процессы и drains.

Пути выше относительно `apps/kilogram-cli/src/ordered_dialog/runtime2`, `crates/kilogram-first-dialog/src` и `crates/kilogram-state/src/vault/indexed_dialog`; frontend monitor — `apps/kilogram-cli/src/terminal_chat/coordinator/monitor.rs`. Это ссылки на фактический код базы, а не обещание уже выполненного sender-restart теста. Продуктовая доработка сейчас не выявлена как необходимая; реальную rehydration следует подтвердить focused implementation checks перед полем.

## Последовательность одного proposed run

1. Fresh synthetic Setup/Auto на A/B; исходные account/device/context pins, обе phase3/current leases, watching и две пустые истории на обоих узлах через принятый initial validator.
2. Закрыть B штатно; обязательные owner/native/typed receipts и исчезновение socket. A сохраняет2сообщения последовательно, дожидаясь materialization/retirement первого protected intent. Дважды зафиксировать прежние keys/event IDs и ровно1строку/контекст на A при отсутствующем B.
3. Закрыть A штатно и доказать старый socket gone/полные receipts. Новый Chat/runtime A стартует в том же Setup/profile. Пока B **всё ещё остановлен**, подтвердить новый instance и сохранённые identities; дождаться только A-local monitor watching. Дважды прочитать `request_status` по исходным keys и local history: прежние event IDs/text/role/ordinal, ровно1строка/контекст, materialized/not-delivered. Ни нового запроса, ни retry. `protected=null` после нового frontend допустимо; неизвестный request/новый event/потеря строки — недопустимы.
4. Только после этих доказательств запустить B в том же профиле. Проверить оба новых instances относительно исходных, неизменные contexts/roles/account/device и advancing own locator revisions; разрешено повторное использование портов после доказанного stop. Fresh Auto reconnect/original90s gate, доставка прежних2events без send/retry. B отправляет2новых online replies; новый A уже watching. Exact final histories и раздельные delivery/notification verdicts после drains.
5. Завершить оба новых клиента, собрать все4 Chat/runtime scopes и2 Setup owners, native Jobs и restore исходных6файлов на каждом хосте. Final passive agents/readiness/originals/process proof. Старые failed evidence не изменяются.

## Адаптер, quota и бюджет

Переиспользовать принятые fixed-path CLI/bootstrap images writer-fix candidate `161405ec…`, обычные agents, Auto, IPC/history/notification validators, per-incarnation cache и restore. Нужна узкая новая sender-restart functional sequence/attempt binding; не общий framework и не ослабление literal accepted-image/source checks.

На фазе3 нельзя вызывать существующий `Normal.monitors` для **двух** хостов или парный admission gate: `pair[1]` закрыт. Использовать существующий `monitor(0, warm=True)`/локальную history и Status API только нового A. Полный парный gate начинается после запуска B. Начальный empty-history validator используется только до отправок, а не для сохранённого sender history.

На **каждом** хосте Setup+2Chat/runtime инкарнации: обычные14+warm13=27records, marker28; writer32records+marker, reader16на scope/32с явным previous scope (`lab_diagnostics.rs:15`, `host.ps1:160–178`). Ничего не архивировать/удалять. Проверять nonce/instance и current+previous PID binding отдельно на A/B. Существующие immutable kind/PID filenames и reader требуют различных4PID внутри сохранённых scopes каждого хоста; PID reuse/collision — отдельный диагностический FAIL, не повод затирать старые файлы или объявлять потерю сообщений.

Mailbox limits неизменны:192commands/512frames на инкарнацию (`test-terminal-t1-2e-mailbox.cs:17`), pending IPC не более2. В live03 у A было одно, у B два Chat scopes; здесь дополнительная работа распределяется между старым/новым A, а не в один mailbox. При реализации посчитать bounded planned/actual commands и запас до192/512; не добавлять бесконечный polling. Agent уже поддерживает3последовательных clean owners на каждом хосте (`lab-agent.ps1:363–382`).

Сохраняем native1000/1015s **на весь общий attempt**, reserve60; controller1800/outer1860, BelowNormal/max2. Connect85, watching30, bounded local pending probes35, initial/reconnect90, runtime probe60/mincall2 — прежние limits. После A-restart без B не ждать заведомо невозможного pair admission. Live03 занимал444.313s application/574s controller; дополнительный штатный A restart и локальные чтения предварительно укладываются в существующий запас, но это оценка, не измеренный новый результат. Реализация должна проверять remaining budget перед фазами и сохранять cleanup reserve; лимиты не увеличиваются ради PASS.
