## Source facts and the precise gap

* `migration_s5_process.rs:16-39`: existing `OwnedChild::kill_wait` and `Drop` call synchronous `Child::wait()` with no time bound. Reusing that destructor after a bounded capture loop would leave the required bounded-return property unproved. Changing it globally would affect legacy/S53 ownership, outside this slice.
* Replacing the destructor with only `kill()` plus a bounded `try_wait()` loop is insufficient for the failure branch. If termination fails or exit is still unconfirmed at cleanup expiry, dropping `std::process::Child` relinquishes the owned process without proving exit. Retaining the handle in a new pending-owner collection requires a defined owner and bounded finalization/containment rule when the capture guard or partially built Controller is dropped. The existing capture/deadline helper has no such API. Merely recording `waited:false` does not satisfy the no-leak contract.
* The existing outer PowerShell watchdog has a Windows Job Object, checks child membership, and can terminate/clean its members (`scripts/migration-s5-l1-deadline.ps1:25-106`). This is useful containment for validation, but there is currently no Rust capture API that verifies this ownership, transfers an unresolved child to that owner, or makes its eventual cleanup receipt part of the status operation. Silently relying on the outer job would weaken the requested local cleanup contract.
* Direct Windows job/cancellation FFI inside this Rust harness would require `unsafe`; workspace Rust policy is `unsafe_code = "forbid"` (`Cargo.toml:73-74`). It is not legitimate to bypass that policy during this slice. A reviewed safe dependency or isolated native test-support boundary would be an additional seam, not an existing accessor.

This is specifically the unresolved ownership/containment branch after failed or unconfirmed termination. It is not a claim that ordinary Windows child termination cannot be polled with a finite deadline, nor that the happy-path capture needs a general process framework.

## Reader design investigated; shortcuts rejected

The locked Tokio is **1.53.3** (`Cargo.lock:6392-6395`). Its actual local `src/process/windows.rs` uses `Blocking<ArcFile>` for `ChildStdio` (line197) and constructs it with `Blocking::new` (line251). `src/runtime/runtime.rs` documents blocking work continuing through shutdown and `shutdown_timeout` returning without stopping it. An async timeout around ordinary Tokio process stdout/stderr is therefore not evidence that owned readers have stopped. No such path was implemented or tested.

A promising safe reader seam already exists: Tokio Windows `NamedPipeServer::create`, `connect`, and `try_read`. Use two locally created inbound pipe servers registered with a current-thread I/O runtime; open synchronous local write ends with `std::fs::OpenOptions` and pass those files as the child's stdout/stderr. Poll both server readers fairly in finite chunks, checking the same effective deadline and per-stream cap on every pass. This avoids wrapping anonymous child pipes in Tokio's blocking stdio adapter and avoids reader threads. Connection, server-registration, EOF and handle-drop behavior still need implementation and real synthetic tests; they are **source-reviewed candidates only**. No claim of proven cancellation/cleanup is made.

Do not substitute `PeekNamedPipe` on synchronous handles and assume it is always nonblocking: [Microsoft documents the multithreaded synchronous-handle caveat](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-peeknamedpipe). [Microsoft's pipe wait-mode documentation](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-type-read-and-wait-modes) distinguishes empty reads, wait modes and overlapped I/O. Neither a raw spool nor detached reader threads are an acceptable fallback.

## Proposed narrow API decision

Approve one explicit test-support ownership boundary before implementing capture. Prefer a safe, scoped Windows child/job owner that exposes bounded spawn/termination/exit observation and retains ownership through cleanup failure, with a clear final owner/containment receipt if a local wait cannot be confirmed. It must own only the capture child, not enumerate or kill processes by name; existing S53 `OwnedChild` behavior stays intact. The implementation must define assignment/spawn failure and guard-construction failure, not just normal timeout. If a native shim or new dependency is selected, review its scope and the workspace unsafe-policy exception/dependency first. Do not infer that approval from permission to run local tests.

Alternatively, the architect can deliberately define an explicit verified handoff to the existing outer job/finalizer, including what Rust retains, how membership is checked, when ownership ends, and where confirmed cleanup is recorded. That changes the current local cleanup premise and should be an explicit contract amendment. This report does not implement the memory observer, result/finalizer composition or a new whole runner.

There is a second verification seam to settle at the same time: an unframed stable synthetic fixture. A clean option is a test-only `harness = false` fixture target with a closed set of benign modes; default/list invocations do no work. Current frozen artifact counting is exactly six for CLI+transport or nine with state (`scripts/cargo-frozen-artifacts.ps1:59-65`). Adding a fixture target would change that accepted inventory, so its fixed executable and expected-count update must be included explicitly. This is not by itself evidence that a new product CLI/config is necessary. A reviewed alternative unframed fixture seam is equally acceptable. Stripping libtest framing from captured JSON is rejected.

## Capture design ready after that decision

1. Put a non-reentrant, thread-affine RAII capture opt-in before `OldOrigin::create` in `Controller::new`; move the guard into Controller and retain it through constructor failure cleanup, continuation, Controller Drop and field destruction. Require the existing managed deadline scope; never silently fall back to raw logs when S54 capture was requested. Do not reset its original deadline, local bound or sequence.
2. Route exact structured `ordered status/status3 --ipc-file ...` queries at `json_cli` before `cli` and its raw error wrapper. This covers `Node::status`, root `old_status`, and direct frozen JSON status calls without a command-string heuristic. Keep all other commands and non-opt-in callers on the legacy path. Starting before `old_pair` ancestry covers early setup; the inspected `old_pair` body itself currently creates contexts/profiles, so that ordering is not a claim that every such setup command is a status query.
3. Add a narrow deadline accessor that reserves the original sequence slot with its effective absolute/local bound and `create_new` destination names. Capture bytes only in memory, cap stdout/stderr independently while reading (1MiB each), drain fairly, and require actual exit observation/wait plus both EOFs. Scope byte buffers with `Zeroizing`; do not claim serde values are wiped automatically.
4. Parse successful bounded original JSON in memory, retain it unchanged for identity assertions, and sanitize a separate clone using the existing exact `public_fingerprints` function. That function replaces each object `keys` field by BLAKE3 of `serde_json::to_vec(keys)` and then recurses through the remaining object/array values. Only the sanitized serialization reaches the first durable stdout write. Stderr remains opaque bounded metadata on success and failure.
5. On malformed/truncated JSON, invalid UTF8, nonzero exit, overflow, deadline, I/O, sanitizer or cleanup failure, return/write only bounded classification, actual code/counts, structured parse location and ownership facts. Never format raw stdout/stderr or a serde parse input into errors. No partial JSON success or raw fallback.

After source/API acceptance and implementation, use edition-correct format, strict scoped Clippy, stable compile-only capture, and isolated new/deadline/sanitizer tests in that order. Actual synthetic tests must cover nested identity preservation/sentinel absence, both-stream pressure, stall and overflow, finite return and actual cleanup/EOF facts. Jobs2/BelowNormal/offline/locked; fresh scratch directories; no actual messenger/profile/store/keys/network. These are pending checks, not results of this submission.
