# Журнал решений

Статусы: `принято`, `предварительно`, `отложено`, `отклонено`.

| ID | Дата | Статус | Решение | Обоснование |
|---|---|---|---|---|
| D-001 | 2026-08-24 | принято | Создавать Kilogram как самостоятельный открытый проект, а не форк Keet. | Полные исходники Keet и спецификация его протокола не опубликованы; проекту нужен собственный проверяемый протокол. |
| D-002 | 2026-08-24 | принято | Основное ядро писать на Rust. | Одно безопасное переносимое ядро для desktop, mobile, headless и relay; независимость от UI и Pear/Bare. |
| D-003 | 2026-08-24 | предварительно | Использовать Iroh как первый P2P transport. | Готовые QUIC, hole punching и зашифрованный relay fallback; решение требуется подтвердить desktop/mobile spike и сравнением с rust-libp2p. |
| D-004 | 2026-08-24 | принято | Использовать MLS RFC 9420 через OpenMLS для группового E2EE. | Не изобретать собственную групповую криптографию; OpenMLS является Rust-реализацией стандарта. Интеграционная модель ещё проектируется. |
| D-005 | 2026-08-24 | принято | Хранить историю как собственный подписанный event log / causal DAG. | Нужны проверяемая целостность, мультиустройство, P2P-репликация и независимость wire protocol от конкретной БД и сетевой библиотеки. |
| D-006 | 2026-08-24 | отклонено | Использовать блокчейн для порядка групповых сообщений. | Детерминированной линеаризации causal DAG и checkpoints достаточно; блокчейн добавляет задержку, Sybil-проблемы и сложность. |
| D-007 | 2026-08-24 | принято | На первом этапе разрешить direct P2P с раскрытием IP собеседнику. | Это упрощает MVP; риск должен быть явно отражён в продукте. |
| D-008 | 2026-08-24 | отложено | Добавить обязательный single-hop/multi-hop relay privacy mode. | Требуется позднее для сокрытия IP; доверенным контактам пользователь сможет разрешить direct P2P. |
| D-009 | 2026-08-24 | принято | Разрешить временное хранение только E2EE-ciphertext на случайных узлах. | Обеспечивает офлайн-доставку без выдачи владельцу узла ключей, содержимого и прикладных идентификаторов; metadata leakage полностью не исчезает. |
| D-010 | 2026-08-24 | принято | Разделить корневую идентичность аккаунта и отдельные ключи устройств. | Компрометация одного устройства не должна автоматически давать корневые полномочия и ключи остальных устройств. |
| D-011 | 2026-08-24 | предварительно | Обычные сообщения упорядочивать eventually-consistent; строгую финализацию применять к security-sensitive операциям. | Мгновенный глобальный total order конфликтует с доступностью P2P-системы при разделении сети. |
| D-012 | 2026-08-24 | принято | Hypercore, Autobase и HyperDHT рассматривать как референсы, не как выбранный фундамент. | Их идеи полезны, но основной вариант должен оставаться независимым от экосистемы Holepunch. |

## Правило изменения решений

Изменение принятого решения должно сопровождаться новым ADR/RFC или явной
правкой этого журнала с причиной, последствиями и датой. Предварительные
решения становятся принятыми только после технической проверки.
