# Журнал решений

Статусы: `принято`, `предварительно`, `отложено`, `отклонено`.

| ID | Дата | Статус | Решение | Обоснование |
|---|---|---|---|---|
| D-001 | 2026-08-24 | принято | Создавать Kilogram как самостоятельный открытый проект, а не форк Keet. | Полные исходники Keet и спецификация его протокола не опубликованы; проекту нужен собственный проверяемый протокол. |
| D-002 | 2026-08-24 | принято | Основное ядро писать на Rust. | Одно безопасное переносимое ядро для desktop, mobile, headless и relay; независимость от UI и Pear/Bare. |
| D-003 | 2026-08-24 | предварительно | Использовать Iroh как первый P2P transport. | Готовые QUIC, hole punching и зашифрованный relay fallback; решение требуется подтвердить desktop/mobile spike и сравнением с rust-libp2p. |
| D-004 | 2026-08-24 | принято | Использовать MLS RFC 9420 через OpenMLS для группового E2EE. | Не изобретать собственную групповую криптографию; OpenMLS является Rust-реализацией стандарта. Интеграционная модель ещё проектируется. |
| D-005 | 2026-08-24 | принято | Хранить историю как собственный подписанный event log / causal DAG. | Нужны проверяемая целостность, мультиустройство, P2P-репликация и независимость wire protocol от конкретной БД и сетевой библиотеки. |
| D-006 | 2026-08-24 | отклонено | Использовать блокчейн для порядка групповых сообщений. | Детерминированной линеаризации causal DAG и checkpoints достаточно; блокчейн добавляет задержку, Sybil-проблемы и сложность. |
| D-007 | 2026-08-24 | принято | На первом этапе разрешить direct P2P с раскрытием IP собеседнику. | Это упрощает MVP; риск должен быть явно отражён в продукте. |
| D-008 | 2026-08-24 | отложено | Добавить обязательный single-hop/multi-hop relay privacy mode. | Требуется позднее для сокрытия IP; доверенным контактам пользователь сможет разрешить direct P2P. |
| D-009 | 2026-08-24 | принято | Разрешить временное хранение только E2EE-ciphertext на случайных узлах. | Обеспечивает офлайн-доставку без выдачи владельцу узла ключей, содержимого и прикладных идентификаторов; metadata leakage полностью не исчезает. |
| D-010 | 2026-08-24 | принято | Разделить корневую идентичность аккаунта и отдельные ключи устройств. | Компрометация одного устройства не должна автоматически давать корневые полномочия и ключи остальных устройств. |
| D-011 | 2026-08-24 | предварительно | Обычные сообщения упорядочивать eventually-consistent; строгую финализацию применять к security-sensitive операциям. | Мгновенный глобальный total order конфликтует с доступностью P2P-системы при разделении сети. |
| D-012 | 2026-08-24 | принято | Hypercore, Autobase и HyperDHT рассматривать как референсы, не как выбранный фундамент. | Их идеи полезны, но основной вариант должен оставаться независимым от экосистемы Holepunch. |
| D-013 | 2026-08-25 | принято | Прикладная device identity не должна совпадать с transport identity Iroh. | Маршрут и transport могут меняться независимо от полномочий устройства; transport Endpoint ID не становится идентичностью аккаунта. |
| D-014 | 2026-08-25 | предварительно | Для M0 кодировать детерминированные signed events через Postcard, подписывать Ed25519 и идентифицировать BLAKE3. | Это минимальный проверяемый Rust-прототип с domain separation; межъязыковой публичный wire format и crypto agility ещё предстоит спроектировать. |
| D-015 | 2026-08-25 | предварительно | Для M0 хранить каждый signed event отдельным неизменяемым content-addressed файлом. | Это позволяет проверить append-only, deduplication, corruption detection и causal frontier до выбора production database; формат на диске и отсутствие at-rest encryption не являются production-решением. |
| D-016 | 2026-08-25 | предварительно | В M0 listener явно задаёт один `allowed requester device`; signed ticket связывает его с listener key и transport Endpoint ID. Sync дополнительно требует, чтобы requester уже был автором conversation; inventory и signed diff session-bound. | Обладатель ticket без разрешённого device key не может сначала внедрить событие, а затем получить историю. Обе стороны доказывают владение ключами до раскрытия events. Это временная граница до Account Root authorization, membership и revocation. |
| D-017 | 2026-08-25 | принято | Reconciliation state machine не должна зависеть от Iroh: session rules используют узкий store trait, а Iroh-specific ALPN и framing вынесены в отдельный adapter crate. | Проверки identity, session binding, exact event sets и continuation можно тестировать без сети; смена Iroh на другой transport не должна менять правила синхронизации. |
| D-018 | 2026-08-28 | предварительно | M0 connection ticket подписывает route policy `auto`, `direct-only` или `relay-only`. `relay-only` отключает IP transports; `direct-only` допускает relay для установления связи и NAT traversal, но блокирует прикладные frames до выбора direct path. | Так тест принудительного relay действительно исключает скрытый direct fallback, а проверка hole punching не ломается отключением relay-координации. Это transport-level M0 policy, а не окончательная модель privacy preferences. |
| D-019 | 2026-08-31 | отклонено | Считать pinning relay-only dialer к автоматически выбранному home relay listener достаточным исправлением. | Внешний retest подтвердил одинаковые `relay_home_url` и `target_relay_url` (`euc1`) на обоих endpoints, но handshake всё равно завершился timeout. Pinning сохраняется как корректная детерминизация маршрута, но сам по себе дефект не устраняет. |
| D-020 | 2026-08-31 | принято | Разрешить listener явно задавать единственный relay через `--relay-url`; URL попадает в подписанный ticket, а relay-only dialer использует тот же relay. | `auto` успешно выполнил внешний exchange через `aps1`, тогда как автоматически выбранный `euc1` дважды не доставил strict relay-only handshake. Явный `aps1` затем успешно перенёс strict relay-only exchange между теми же двумя сетями. Override нужен для детерминированного M0 и является прототипом согласованного privacy relay selection; production failover ещё предстоит спроектировать. |
| D-021 | 2026-08-31 | принято | В M0.4 использовать durable event set как checkpoint корректности sync после обрыва, не вводя отдельный переносимый cursor поверх full-ID inventory. | Полученные events сохраняются до подтверждения и идемпотентны; свежий session-bound inventory после reconnect вычисляет только остаток. Отдельный token пока не уменьшил бы полный inventory и потребовал бы решить staleness/snapshot semantics. Подписанный cursor проектируется вместе с compact Merkle/range summary. |
| D-022 | 2026-08-31 | принято | В M0.5.1 `AccountId` является отдельным Ed25519 public root key; root secret подписывает только device certificates и revocations. Валидный отзыв навсегда запрещает конкретный device key, поэтому повторное добавление требует нового ключа. | Прямая публичная проверка не требует key-resolution слоя; отделение root от device ограничивает полномочия обычного устройства; монотонный отзыв исключает двусмысленное повторное доверие уже скомпрометированному ключу. Seed/recovery, protected root storage и distributed authority log остаются отдельными решениями. |
| D-023 | 2026-08-31 | принято | M0.5.2 заменяет `--allow-device` и known-author на ticket v3 с listener certificate, allowed requester Account ID, явный expected peer Account ID и device-signed Endpoint-bound authorization proof до application data. Revocations проверяются из caller-supplied trusted files. | Новый сертифицированный device аккаунта может синхронизировать пустую историю без synthetic event; другой аккаунт, чужой key или известный revoked device отклоняются до event/inventory. Явный `--expect-account` не позволяет подменить весь ticket другим self-consistent account. Файлы отзывов дают проверяемую validity, но не freshness/completeness; authenticated authority-log distribution остаётся отдельным этапом. |
| D-024 | 2026-08-31 | принято | M0.6.1 публикует root-signed полный permanent-revocation set как `AccountAuthoritySnapshot(revision)`, передаёт его в ticket v4/session authorization v2 и сохраняет max-seen revision каждого peer account. Старые revision и разные snapshot одной revision отклоняются. | Snapshot доказывает completeness на конкретной root revision и устраняет ручные списки файлов. Anti-rollback действует после наблюдения новой revision, но без discovery/gossip/witness не доказывает глобальную freshness при первом контакте. Legacy root с authority operations без durable revocation log не может безопасно объявить snapshot полным и не мигрируется автоматически. |
| D-025 | 2026-08-31 | принято | В M0.6.2 один owner Account Root подписывает полный add-only `ConversationMembershipSnapshot`, а каждое сетевое/синхронизируемое событие переносит `DeviceCertificate` и `AccountAuthoritySnapshot` автора в `AuthorizedEvent`. Локальный membership является trust anchor и не принимается от peer автоматически. | Это даёт проверяемую цепочку membership → account → device → event и разрешает безопасно отклонять history автора вне разговора. Add-only честно откладывает removal до ordered security log и MLS epoch. Обязательный immutable authorization sidecar сохраняет стабильный Event ID, но делает старые M0 events без Account proof несовместимыми и немигрируемыми автоматически. |
| D-026 | 2026-08-31 | принято | M0.7.1 использует RFC 9180 HPKE Base mode X25519/HKDF-SHA256/ChaCha20-Poly1305 как pairwise payload baseline. Root-signed DeviceCertificate v2 связывает отдельный encryption public key, а каждый encrypted text event содержит canonical box для текущего sender device и одного peer device; plaintext-варианта в event schema нет. | Стандартизованный single-shot primitive позволяет проверить E2EE-композицию с signed DAG/store/sync без самодельной криптографии. Внешняя Ed25519 event signature аутентифицирует sender и весь ciphertext envelope. Решение намеренно не обещает forward secrecy/PCS и не заменяет будущие asynchronous prekeys/Double Ratchet или two-member MLS. |

## Правило изменения решений

Изменение принятого решения должно сопровождаться новым ADR/RFC или явной
правкой этого журнала с причиной, последствиями и датой. Предварительные
решения становятся принятыми только после технической проверки.
